## Plain-language summary

The HR "backdate worklist" lists months that were already sent to payroll and then changed underneath — for example, someone's part-time fraction or agreement code was corrected with an earlier effective date. For some of those months the system *knows* it cannot recalculate correctly (the change falls in the middle of the month, and the calculation engine cannot yet split a month in two for the rules that look at whole weeks). The screen already hides the "Recalculated" button on those rows. But the server never checked — anyone calling the API directly could record "recalculated" on a month the system itself says cannot be recalculated.

The owner ruled (2026-09-22) not just to block that, but to **split the verb**: add an honest outcome, **"Håndteret manuelt"** (handled manually), for when a person really did sort the month out by hand. With that available, refusing the false "recalculated" costs nobody anything, so the server now refuses it — on the locked row, for every role.

While tracing this, the refinement found a real payroll defect: when an employee's **agreement code changes mid-month**, the payroll recalculation and the everyday export compute the days after the change under the old agreement and write the result as if nothing happened. S144 makes the calculation *see* that change and refuse — with a 422 that says how many segments and which causes, rather than today's bare 500. **Consequence to know about:** until QUAL-149/150 land, a month with a mid-month agreement-code change cannot be exported at all; it goes to the manual path. A refusal beats a wrong payslip.

**What changed in draft 2, in one paragraph.** Both reviewers caught the same hole: draft 1 asked for "proof the tests fail without the change" by reverting the change *after* it had merged — which either reverts nothing or deletes the very types the tests compile against, so the "failure" would be a compile error, not the behaviour going wrong. Draft 2 replaces that with **mutation testing at the gate**: with the real code on master, a tester breaks *one behaviour* on purpose in a throwaway copy (for example, "write an empty block set on a blocked row") and shows the named test turns red. Every such test now names its mutation. The reviewers also found places where a test was claimed to prove something it could not (the stamp on the existing Dismiss verb; the wiring from database to screen), one refusal branch with no test, and a brief that would have told an agent to filter out rows it must keep. Each is fixed below; the disposition list is at the end.

**What changed in draft 3, in one paragraph.** Two rulings. **R6:** the four mutation tests that need a database (they guard the stamp and the payroll hydration — the two things this sprint exists to make true) will be *watched* going red in a real CI run, not just argued in a comment. Because CI only runs on `master` or on a pull request to it, that run happens on a throwaway branch with a draft pull request that is closed and deleted as soon as the run reports — evidence, never something to merge. **R7:** the screen will not display the recorded block set on resolved rows, because the screen never shows resolved rows; the recorded fact still lives in the event, the row and the API, and a "show resolved rows" toggle is on the backlog instead. Folding R6 in exposed two things the ruling's premise did not account for (N-3, N-4 under "Needs a ruling"): two of the four mutations cancel each other out if applied together, and every mutation also turns a few *other* S144 tests red, so "exactly four red" needs a precise meaning.

**What changed in draft 4, in one paragraph.** Both of draft 3's open items were ruled: two evidence runs (R8), and "exactly the list written in advance, nothing else" (R9). The external reviewer then found that the plan *described* two runs but could not *produce* them: the tester was to put both evidence commits on the branch before anything was pushed, so the first push would already carry the second state and CI would only ever see that one. Draft 4 spells out the order step by step — push the first commit alone, watch it, then move the same branch forward to the second commit, watch that — in a short numbered **close sequence** (checkpoints C-1..C-9) that the Orchestrator executes. The reviewer also found a promised "should stay green" check that could never run (it lived inside a test that the mutation stops half-way), so that check is now its own test, and every entry in both runs' expected lists is a named test. Finally, the reviewer found the evidence schedule out of order: Step 7a was meant to read material that was only produced after it. The fix follows the S143 house pattern: the reviewed commit is fixed first, the evidence is prepared from it before Step 7a, the runs happen after the close is pushed, and their results land in a small docs-only follow-up commit — nothing tested is ever amended.

## How the waves are built — read before the ledger

Three facts shape the order, and each came from a past sprint:

1. **Pins define done, but master must compile.** Pins that only speak HTTP or SQL compile against today's code, so they land first (TASK-14401). Pins that name a type or member S144 creates (the new exception, the planner's structured members, the mapping function) cannot compile until the implementers merge. Those are **authored in wave 1 from the spec in their own worktree** (TASK-14405) and **merged at the wave-2b gate** — the S141 convention ("pins are authored RED-first from the spec concurrently, but the task completes at the wave gate", `SPRINT-141.md:325-329`). The implementers are given those pins' names and assertions in their briefs as the definition of done.
2. **RED evidence has two mechanics, and neither is "revert after merge"** (`docs/AGENTS.md:162-180`, § "RED evidence for a pin that cannot compile before the implementation exists"). A compile-today pin proves RED by running before the implementation exists. A new-API pin proves RED by a **named mutation at the wave-2b gate**, in an isolated `git worktree` from master, run by a re-spawned `test-qa`; a compile failure on revert never counts. **Docker is unavailable locally**, and every Regression pin here is `[Trait("Category","Docker")]`: for those, the RED is argued in the docstring ("Red conditions", the house style — `BackdateWorklistEndpointTests.cs:264-271`), GREEN is observed in the watched CI run at close. The four Docker-gated **mutations** (M-1, M-2, M-3, M-14) are additionally **observed** in watched CI runs on a throwaway evidence branch at close — **ruled R6** (N-1 → (B)), in **two runs on one draft PR** — M-1 + M-2 + M-14 first, M-3 alone second, because M-1 and M-3 cancel each other in one build — **ruled R8** (N-3 → (A)). The exact order is the **close sequence** below (C-1..C-9); TASK-14405 re-spawns 2 and 3 and O-6 point to it.
3. **The planner change comes before the payroll change.** The payroll task hydrates a `BoundarySources` member and reads refusal members that the rule-engine task creates, so it branches from master **after** TASK-14402 merges (wave 2b). The backend worklist task is independent of both and runs alongside the rule-engine task (wave 2a).

## Close sequence — checkpoints (executed by the Orchestrator on Opus; Fable-seat judgments marked)

*Plain language:* the sprint is reviewed on a fixed commit; the deliberate-breakage evidence is prepared from that same commit before the review, so the reviewers can read exactly what will be broken; the two evidence runs happen after the real close is pushed; and their results are written down in a small docs-only commit afterwards — the S143 "CI-green backfill" pattern (`b49f781` recorded the CI run for `5e78941` without amending it). Nothing that was reviewed or tested is ever amended. Shorthand: **K** = the candidate commit, **E1** / **E2** = the two evidence commits.

1. **C-1 (wave-2b gate).** TASK-14405 re-spawn 2, after its unit-mutation run, resolves both runs' expected-red and expected-green lists (TASK-14405, "Expected lists") to `FullyQualifiedName`s from master with `dotnet test <project> --list-tests`, and reports any name that does not resolve. **Fable seat:** reviews and freezes the lists (R9). Any later change to them is a Fable ruling.
2. **C-2 (after wave 3's O-1 gate).** O-4 docs written, with the Step-7a outcome and the evidence results left as marked placeholders. Commit **K** on master, message `S144 close: <summary>` — deliberately *without* the phrase "sprint close", so the guard treats it as an ordinary commit (`.claude/hooks/sprint-close-guard.ps1:80-92`; S143's `89d3daa` "S143 close: …" is the precedent). Not pushed.
3. **C-3.** TASK-14405 re-spawn 3 from **K** — if C-3 is being repeated for a replacement K, first remove the previous unpublished evidence worktree and branch (`git worktree remove <path>`; `git branch -D s144-red-mutations`) and recreate them from the new K; once the branch has been published, corrections are fast-forwards on the tip instead (C-6): **E1** = K + M-1 + M-2 + M-14; **E2** = a child of E1 whose tree is K + M-3 alone. `dotnet build` 0 errors and the non-Docker suites green **at E1, and again at E2**. Reports both shas and `git diff K E1` / `git diff K E2` verbatim. Nothing pushed.
4. **C-4 — O-5 Step 7a.** Both lenses, base `2e7d5b1`, `reviewed-against-commit: <K>`. The lenses read the frozen lists (C-1), re-spawn 2's mutation table, and both evidence diffs (C-3). A code-touching Step-7a fix makes a new **K** → repeat C-3 on it and run the verification cycle `docs/WORKFLOW.md` step 7a requires.
5. **C-5 — close commit + O-6.** `S144 sprint close — …`: a docs-only child of the reviewed K (the Step-7a outcome in `SPRINT-144.md`), which is what the guard checks (`reviewed-against-commit` must prefix HEAD, `sprint-close-guard.ps1:170-183, 273`). Confirm `git diff --stat K HEAD` lists only `docs/**`. Push master; watch the CI run on the close sha to green. If it is red: a post-close fix (with its own Step-7a cycle, `docs/WORKFLOW.md` step 7a "Post-Step-7a coverage"), and C-3 is repeated on the fix sha before C-6 (the fix sha then takes K's role in C-6..C-9, and the evidence diffs are re-read against it by that fix's Step-7a cycle).
6. **C-6 — evidence run 1.** `git push origin <E1>:refs/heads/s144-red-mutations` (E1 is the branch tip; E2 is not on origin). Open the **draft** PR to `master`, body first line "EVIDENCE ONLY — deliberate mutations for S144 RED evidence; never merge; closed and deleted when both runs report". Watch to completion; confirm the run's `headSha` equals E1 (`gh run list --branch s144-red-mutations --json databaseId,headSha,event,conclusion`). *Two things to know:* CI on a pull request tests the PR merged into `master`, which here adds only the close commit's `docs/**` change, so the tested code is K + the mutations; and these are `pull_request` runs, so their deliberate red cannot reach the guard's CI-health check, which reads only `push` runs on `master` (`sprint-close-guard.ps1:316`). **Fable seat (R10):** compare the red set to the frozen run-1 list. Mismatch → re-spawn 3 adds a corrected commit on the tip (tree = K + corrected M-1/M-2/M-14; C-3 checks), push as a fast-forward, repeat run 1 — never interpret; E2 is then re-made as its child (same tree, K + M-3).
7. **C-7 — evidence run 2.** Only after run 1 matches: `git push origin <E2>:refs/heads/s144-red-mutations` — a fast-forward, which fires the PR's `synchronize` event (`.github/workflows/ci.yml:6-7`). Watch; confirm `headSha` equals E2; **Fable seat:** compare to the frozen run-2 list; a mismatch is handled as in C-6.
8. **C-8.** Close the PR unmerged; `git push origin --delete s144-red-mutations`; `git branch -D s144-red-mutations`; confirm the branch is gone on both sides.
9. **C-9 — docs-only follow-up commit (seals the close, R10).** Never an amend of the close commit. It records: the CI-green line for the close sha; per run, the run id, the head sha (E1 / E2), each red test with its assertion message against the frozen list, "matched"; the PR number and "closed unmerged, branch deleted"; that `claude-code-review.yml` output, if any, was ignored; the O-7 routing row. *How it relates to what was tested:* it touches only `docs/**`, so the code it sits on is exactly the close sha's; E1 and E2 are K plus the mutations only, and K differs from the close commit only in `docs/**` (checked in C-5). Push; watch green; teardown.
