## Plain language — why

Every request to the system carries a login token, which the backend validates before it does anything. S149 moves the token library twice: IdentityModel 7 → 8 in wave 1, then the .NET 10 JwtBearer in wave 3. A library upgrade can change validation without anyone noticing:
- it can rename claim types, so roles stop matching;
- it can accept a shorter key;
- it can change the clock-skew tolerance.

Today's unit tests read tokens with an old handler, not the one the middleware uses. The two host tests that run the real middleware carry no `scopes` claim and no negative case. **Your task writes down, as executable tests, exactly how the real validation path behaves today** (accepts, rejects, and what the app sees), so that waves 1 and 3 must reproduce it unchanged.
