## Plain language — why

When someone leaves, their access to **their own** data must end the day after their last working day, whatever their role. Ordinary employees are covered at the screens they use (TASK-14710). But a leader, an HR user or an administrator reaches their own record through **admin** routes, and almost all of those ask one shared question first: "does this person's organisation scope cover the employee?" That question never asked whether the actor **is** the employee. This task adds that one test, "a departed self is refused", inside the shared validator, so about two dozen admin routes close at once. Thirteen routes check something else first (an organisation, an assignment id, a unit, the caller's own id, or nothing at all), so the same test goes into each of them by hand, and one more route that the validator does cover (removing a manager) gets a check on the people it rewrites as a side effect. The owner asked for the complete list, so this brief carries a census of every write route in the three hosts, each closed or classified out with a reason, sorted by one rule (the "subject key", below). Access to **other people's** data is untouched: a manager keeps reaching a leaver during the 5-day grace, and HR keeps acting on leavers.

4. **The inline guard rule (R-31, F4, P-1) — one rule at every route below.** *Which routes (the subject-key rule, P-1):* a route is guarded when the departed actor's own id is the **subject key** of any employee-keyed row the route inserts, updates or closes — taken from the route, the body, or derived inside the transaction. The subject keys are `users.user_id`, `role_assignments.user_id`, `unit_leaders.user_id`, `reporting_lines.employee_id` and `manager_vikar.absent_approver_id`. An id that appears only as the **holder** of authority over someone else (`reporting_lines.manager_id`, `manager_vikar.vikar_user_id`, a replacement in `/remove`'s map) is classified out: TASK-14712's acting-user rule makes a departed holder's authority inert from D+1 at every read that honours it. *How:* when the actor id equals the subject's id (Ordinal; a null or empty actor id never matches) **and** `DepartedSubject.IsDeparted(subject, today)` holds, answer **403** `{ error = "Access denied", reason = DepartedSubject.DenyReason }` **before any write**, and log a WARNING naming the clause ("departed-self") and the route. `today` is the handler's single read (`TimeProvider` + `CopenhagenBusinessDate.Today`; add the `TimeProvider` parameter where the handler has none). Where the route already reads the subject active-only, reuse that read (a deactivated self already answers 404 there). Where it reads no subject, read it **only when the identity matches**, with the terminated-inclusive read, **deny-only** (it never admits anyone; name it in `DepartedSubject`'s doc). A subject that cannot be read at all is not refused by this guard; the route's own outcome applies. **A guard that runs inside a transaction fires before that transaction's first write** (an advisory or row lock is not a write); a refusal rolls the transaction back. **Consequence clause (P-10).** A row whose subject key is the actor is classified out when its write is **forced by a permitted write to another person** and the row could not have survived that write whichever way: `/remove` of X closes every open stand-in row where X is the stand-in (Step 4, `ReportingLineEndpoints.cs:1589-1595`; the predicate `absent_approver_id = @userId OR vikar_user_id = @userId` at `:3045`), and a cross-organisation transfer of X in `PUT /api/admin/users/{userId}` closes every row involving X (`AdminEndpoints.cs:2452-2474` → `ManagerVikarRepository.cs:347-367`, the UPDATE at `:353-356`). If X is the departed actor's own stand-in, the actor's own row closes as a side effect — but it is dead either way: a deactivated stand-in is skipped (`ReportingLineRepository.cs:1209-1212`, S74 R3b) and a transferred one is outside the organisation the row is bound to (ADR-038 D12). The actor's choice does not shape their own record, so no guard is added; two boundary facts pin it (TASK-14703-T). Contrast `/remove`'s rewrite of the actor's own **reporting line** to a replacement the remover chose, which is guarded (below). These two are the only derived closures of `manager_vikar` in `src`.
