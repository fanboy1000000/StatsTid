# TASK-14519 — the local-profile activation key from the dated record (payroll-integration, A.5)

**Plain language.** When payroll plans a month, it asks one more question: did the employee's organisation switch on a local agreement profile partway through the month? A switch-on is a boundary that splits the month, and under Stage A a split month is refused. Today that question is asked with the **request body's** organisation, agreement and OK version. Every other planning and evaluation input now comes from the employee's dated record (R-10, R-11, R-12, A4). A stale body for a past month can therefore ask the wrong history:
- it can invent a boundary, so the month is refused for nothing;
- it can miss one, so a month that should split is calculated as one piece;
- either way, the manifest's cause summary records the wrong reason.

**No paid figure changes.** The Rule Engine applies no local profile (R-20, fact b); a local profile is a boundary source and nothing else in payroll. **Replay is unaffected,** because it loads the frozen plan and never plans. Registered as **QUAL-203**.

**Paste with:** adjudicator R-20 (`docs/sprints/SPRINT-145.md` § "Wave A.5"); ADR-017 D9c and D10; the R-10, R-11 and R-12 records.

**Depends on:** TASK-14513 merged (the same file, `PeriodCalculationService.cs`).

**Do.**
1. **Key the lookup per (agreement, OK-version) interval, on the dated record.** Replace the single call at `PeriodCalculationService.cs` (~`:1567-1578`, `GetActivationsInPeriodAsync(profile.OrgId, profile.AgreementCode, profile.OkVersion, …)`):
   1. Cut `(periodStart, periodEnd]` at the interior agreement-code dates (`histories.AgreementCodeEffectiveDates`) and the interior OK transitions (`okTransitions`). Both are known before the planner runs, and neither depends on activations, so there is no circularity.
   2. For each interval, resolve the dated record at its first day (`TryResolveDatedProfileAsync`; when `_profileResolver` is null the caller's profile is the record, the same rule the dated `WtmNaturalKey` applies). Take its `AgreementCode` and its `OrgId` (the resolver fills it from the record, `EmploymentProfileResolver.cs:251`), and that day's OK version (`OkVersionResolver.ResolveVersion`, a pure function).
   3. Call `GetActivationsInPeriodAsync(org, agreement, ok, intervalStartExclusive, intervalEnd)` per interval, then take the union, sorted. An activation on an interval's first day is already a boundary there (`AddIfAbsent`). The detector ranks `LocalProfileActivation` above `AgreementCodeChange` (ADR-017 D9b's slot; S144 R1 ranked the agreement change only above the profile change), so an activation handed over on a key-changing cut would hide the agreement change; the strict-greater lower bound keeps it out, and the cut's own cause labels the date (R-26), so the strict-greater lower bound is right for every interval.
   4. The interval starts are a subset of `CandidateSegmentStarts`. Share the dated resolutions (memoize by date), so no extra reads are made.
2. **The body's `OrgId` is no longer read here.** ADR-017 D9c's "no org → no profile boundaries" keeps its meaning with the record's org.
3. **An agreement change on the 1st is not interior.** The record at `periodStart` already carries the new code; no special case.
4. **Comments.** State where the key comes from, and why per interval.
