## Plain language — why this task exists

When HR corrects someone's history after a month was sent to payroll, the HR worklist flags that month ("re-plan it"). It also marks a month that **cannot** be recalculated in the system, and the server then refuses the "Recalculated" answer for it (409), so nobody can record a recalculation that could not have happened (QUAL-165, built in S144).

Today that marker follows the old rule: **any profile, category or agreement change strictly inside the month blocks it** (QUAL-149 / QUAL-150). Stage B makes such months payable. The one case that stays manual is an **agreement change in the middle of a Monday–Sunday week** the month settles (Q5 (c)): a week cannot be judged under two agreements. Payroll already decides that case with one shared rule, `WeeklyContext.MidWeekAgreementChange`.

This task makes the worklist use **the same rule**, under one new register id for the residual. Without it the worklist would keep blocking months payroll now pays. Since Stage A, it also misses a month payroll refuses: an agreement change on a weekday 1st, or in the previous month's last days, which the month's first week includes. That is the drift refinement A8 names (`:421`).

## Contract (the WHAT)

1. **One new register id for the residual**, the Stage B row the Orchestrator opens before dispatch: **`QUAL-209`** (registered at B.0, `quality-finding-register.md:432`). It is a constant on `BackdateWorklistDerivation`, working name `RecalcBlockedAgreementMidWeek`.
2. **`RecalcBlockedByForTrigger(kind, effectiveFrom, year, month)`**, same signature, same callers:
   - `AGREEMENT_CODE_CHANGE` → the residual id **iff** `WeeklyContext.MidWeekAgreementChange(WeeklyContext.SettledWeeks(first, last, cutoff: null), [effectiveFrom])`, where `first`/`last` are the month's first and last days; otherwise null. This covers an interior non-Monday change, a weekday 1st, and the previous month's last days on the next month's row (Fact 4). A Monday change never blocks.
   - `PROFILE_CHANGE`, `EMPLOYMENT_CATEGORY_CHANGE` → **null**: a profile or category split is now payable per segment (refinement `:702`).
   - `PRIOR_MONTH_REOPENED` and unknown kinds → null (unchanged).
   - SETTLED_YEAR rows → empty (unchanged).
3. **The set overloads, the locked snapshot, the GET fields and the 409 are unchanged in code.** They inherit the new answer because they call the one core. The server 409 and the Global-Admin gate stay (QUAL-165).
4. **The two retired ids** stop being derived. Rows already resolved keep their stamped `resolution_blocked_by` (refinement Assumption 11; reseed makes it moot).
5. **Comments and doc text** (Fact 5) state the Stage B rule. Code in the endpoints and the contracts is unchanged.

*Hints (HOW):* the predicate call can be one local; whether to keep `IsStrictlyInsideMonth` (unused by the derivation afterwards) or retire it with its fact is your choice; report which. Remove the two old constants if nothing references them.

**Ruled at B.0 (R-55): draft as written; the drift is QUAL-210.** *What that means:* the worklist cannot see the leaver's settlement cutoff or the R43 hire filter (Fact 3). With `cutoff: null`, a leaver's last partial week is judged by the month holding its Sunday, while payroll judges it by the leaver's last day, so the worklist **under**-blocks a leaver whose last partial week holds the change (an audit-quality gap; no money moves). With no hire filter, a hire-dated agreement row on a non-Monday is judged a change, so the worklist **over**-blocks it. Feeding the employment window into the derivation would be a cross-context read inside the locked snapshot, outside Stage B. Do **not** add a window or a filter here; TASK-14524's two `KnownDrift_QUAL210_…` facts pin both divergences, so a later fix turns them red on purpose.
