## Plain language — why this task exists

Payroll refuses every month in which something changes partway through (hours, position, agreement). The refusal comes from a label each rule carries. Overtime and the norm rule are labelled **"aligned window: never cut this rule's window in two"**. When a month has two parts, the planner sees that label and refuses the whole month.

Stage A made that label out of date. Since Stage A, payroll no longer runs overtime, the norm check or flex once per part of the month: it sends the **whole month** to the Rule Engine in one call, week by week, with each day's own contract. These three rules are therefore never cut in two any more. They need a new, truthful label: **"timeline-aware: evaluated once across the whole plan, with per-day context; never split"**.

This task adds that label, gives the three rules it, and teaches the merge step what the label means: **exactly one result goes through; two results for such a rule means the design was broken, so it fails loudly**. On its own this task does not yet make split months payable. Payroll still hands the planner rules it never runs (the weekly norm and two rest rules, which keep their "aligned window" label), so the planner still refuses. TASK-14522 removes that last cause in wave B.2.

## Contract (the WHAT)

1. **A fifth split behaviour, appended:** `SplitBehavior.TimelineAware`, documented as "evaluated once across the whole plan with per-day context; never split" (refinement `:430`). **Append it after `Reject`** so the existing integer values stay stable on the wire (the QUAL-002 ordinal-stability precedent, `BoundaryCause.cs:93-95`).
2. **A fifth merge kind, appended:** `MergeStrategyKind.SinglePlanEvaluation` (after `Custom`) and `MergeStrategy.SinglePlanEvaluation`. Its meaning: **the rule was evaluated once for the whole plan; exactly one result goes through unchanged; two or more is a contract violation** (`PlannerInvariantViolation` naming the rule id and the count, never a date). An empty or null list keeps the existing pre-guard. Update the "(4 values)" doc.
3. **The merger arm** in `CalculationResultMerger.Apply`: one result → returned unchanged (same instance, norm totals intact); two or more → throw as above. `ComplianceCheckResultMerger` is unchanged (it already throws on an unknown kind).
4. **`ResolveDefault`:** `(TimelineAware, Calculation)` → `SinglePlanEvaluation`. `(TimelineAware, Compliance)` has **no default** (throws, like a Mergeable rule without an override), because the compliance merger has no single-plan arm and throws on an unknown kind (`ComplianceCheckResultMerger.cs:62-71`). *(Drafter's proposal; the refinement names only the calculation case. Ruled at B.0, R-68: stands as drafted; `Register_TimelineAwareCompliance_WithoutStrategy_Throws` is kept.)*
5. **The registrations:**
   - `OVERTIME_CALC` → `(Window, TimelineAware, Calculation)`, default merge;
   - `FLEX_BALANCE` → `(CrossPeriod, TimelineAware, Calculation)`, default merge (the explicit `Custom` override is removed);
   - `NORM_CHECK_37H` → **registered** as `(Period, TimelineAware, Calculation)`, default merge;
   - `NORM_CHECK_WEEKLY`, `NORM_CHECK_MULTIWEEK`, `NORM_CHECK_ANNUAL` and every rest and compliance rule **unchanged** (refinement `:432`: the rest rules keep `AlignedWindow`).
   - The inventory is then 17. The `Span` values are the drafter's proposal (ruled at B.0, R-68: stands): the two existing rules keep theirs; `NORM_CHECK_37H` takes `Period`, because its totals cover the month's own days. `Period` is descriptive only: the planner reads no `Span`.
6. **The payroll converter** (`HttpRuleClassificationProvider.cs:240-247`) maps `SinglePlanEvaluation` to `MergeStrategy.SinglePlanEvaluation`. No other payroll file changes in this task.
7. **Comments:** the registry's class doc (`:22-26`) and inventory comment (`:105-108`) state the Stage B classification; the `SplitBehavior` and `MergeStrategy` docs describe the new values.
8. **No change** to `PeriodPlanner.cs`, to `RuleRegistry.EvaluateTimeline` (`:399-444`; Stage A's MD-39, MD-41 and MD-42 patch that method, and R65 re-observes them if it changes), or to any dispatch path.
