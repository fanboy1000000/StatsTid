## Plain language — why

Stage B's new tests must be shown able to fail. Most of them need a database (Docker), which this machine cannot run. So the code is broken on purpose in a few known ways on a throwaway branch, and CI must turn red **exactly** the tests listed for each break, and nothing else.

Stage A taught three lessons that bind this task:
- **R-51:** list the cases of the *code condition* a breakage changes, not the scenario the plan tells. EA-3 failed because "the increase branch" also covered first bookings.
- **R-52:** CI tests the branch merged into master, so master must be an ancestor of the branch.
- **Fact 3:** CI stops at its first red step, so a breakage that turns a Unit test red cannot ride a CI run. It is observed locally instead, with a ruling.

**The order (R-53).** At the B.3 gate this task decides each run's breakages and saves them as patch files. The whole-sprint review (Step 7a) reads those patches. Only after the close commit is pushed and green does a re-spawn of this task build the throwaway commits, on top of that pushed commit, by applying the saved patches unchanged. Building them last is what makes master their ancestor (R-52); applying the saved patches unchanged is what makes the review's object and the CI run's object the same thing. If the code changes after the patches are saved (a review fix, or a fix for a red close run), the patches are re-cut on the new code and re-frozen if they differ (R-83).
