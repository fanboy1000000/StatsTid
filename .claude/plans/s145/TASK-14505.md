# TASK-14505 — the week-by-week Rule Engine (rule-engine, A.1a)

**Scope.** Your declared scope is `src/RuleEngine/**` and `src/SharedKernel/**/Calendar/**`. The Orchestrator authorizes one cross-domain file: new `src/SharedKernel/StatsTid.SharedKernel/Models/TimelineEvaluationResponse.cs`. It is shared because payroll deserializes it, on the `FlexEvaluationResponse` precedent (`Models/FlexEvaluationResponse.cs:7`). No `src/Orchestrator/**`: the weekly pipeline needs no code change, because the HTTP contract is kept (refinement `:271`). No tests: TASK-14505-T migrates them on your branch.

**Why.** The overtime, norm and flex rules compare a period's total with one week's norm (`OvertimeRule.cs:25-29`; `NormCheckRule.cs:170-171`; `FlexBalanceRule.cs:23`), so a month is judged as one giant week. This task makes the rules work day by day and week by week. Each weekday carries its own norm from that day's contract (Q2), and each week is settled by the month containing its Sunday, dated that Sunday (Q3). It also leaves one arithmetic path, not two.

**Paste with:** refinement A2 in full (`:232-272`), the precision rule (`:548`), Q2 and Q3 (`:482-502`), Assumptions 1–3 and 5 (`:531-535`), the Stage A criteria "Weekly judging" through "Screen parity" (`:582-629`).

**Facts.**
- Config is resolved per (agreement, OK version, position) (`RuleRegistry.cs:211, :258`; `AgreementConfigProvider.cs:21-24`). Position overrides change `MaxFlexBalance`, `NormPeriodWeeks` and `WeeklyNormHours` (`src/SharedKernel/StatsTid.SharedKernel/Config/PositionOverrideConfigs.cs:16-21`, N7). Every live `WeeklyNormHours` is 37.0 (`CentralAgreementConfigs.cs:20` and nine siblings).
- The OK boundary is 1 April 2026 (`OkVersionResolver.cs:18-19`).
- The norm rule emits one `NORMAL_HOURS` per entry it is given (`NormCheckRule.cs:179-186`). Annual mode is days ÷ 365 (`:114-116`).
- The flex payout line is built at `FlexBalanceRule.cs:64-75` and used by the `/evaluate-flex` route (`RuleEngine.Api/Program.cs:46-94`).
- `AbsenceRule`'s default credit is `7.4 × fraction`, unrounded, used only when an absence carries 0 hours (`AbsenceRule.cs:13, :46-48, :81-83, :98-100`).
- The screen computes `Math.Round(WeeklyNorm × fraction / 5, 2)` on weekdays and 0 at weekends (`DailyNormCalculator.cs:28, :153`).

**Do.**
1. **`DayNorm` and `WeeklyContext`**: pure, no I/O. Write an ADR-002 note in the report: rule arithmetic shared by the engine, payroll and the screen, one implementation (R11).
2. **The core.** It follows the R6 window table (refinement `:245-251`):
   - Overtime and merarbejde run per settled Monday–Sunday week. The norm and both thresholds are per covered weekday via `DayNorm` (thresholds from `OvertimeThreshold50/100` × that day's fraction ÷ 5). Lines are dated on the settlement day.
   - Norm totals and `NORMAL_HOURS` lines cover only the covered days inside `[PeriodStart, PeriodEnd]`; never a context day.
   - Weekly and multi-week modes take the per-day sum; annual mode takes days ÷ 365 per piece. `NormPeriodWeeks` is reported from the last covered day. A week's mode is the Sunday's.
   - Flex is settled once, on the last covered day in the period, at the cap in force that day: delta = worked + credits − (per-day norm − reductions) over in-period covered days; one `FLEX_PAYOUT` dated that day.
   - **Days covered by no piece are not evaluated.** That is how a starter's opening week counts norm only from their first day, and how a legacy call's opening partial week counts only in-period days.
   - *Hint (HOW):* the cutoff unifies the leaver (last employed day) and the legacy call (the period's last day, refinement `:268`).
3. **The endpoint.** It resolves each piece's config per OK-version date (splitting pieces at OK transitions), calls the core, and returns `ConfigFingerprint.Compute` over the configs it resolved (refinement `:369`), plus `EvaluationModel`.
4. **R8 + R34.** `/api/rules/evaluate` for `OVERTIME_CALC` and all four norm ids, and `/api/rules/evaluate-flex`, build a one-piece timeline `[periodStart, periodEnd]` from the request profile with `SettlementCutoff = periodEnd`, and run the core.
   - **The forced mode (R34).** The registry dispatch (`RuleRegistry.cs:215-218`) passes `ForcedNormMode` and `NormRuleId`: `NORM_CHECK_37H` → `null`; `NORM_CHECK_WEEKLY` → `Weekly`; `NORM_CHECK_MULTIWEEK` → `MultiWeek`; `NORM_CHECK_ANNUAL` → `Annual`. Each id's result keeps its own `RuleId`, so `NormCheckRuleTests` for those ids move only by the four labelled changes (Do 6).
   - **Retire** `OvertimeRule.Evaluate`, every public `NormCheckRule` evaluate method (`Evaluate`, `EvaluateWeekly`, `EvaluateMultiWeek`, `EvaluateAnnual`) and `FlexBalanceRule.Evaluate`. Keep only the constants and pure helpers the core uses.
   - `SUPPLEMENT_CALC`, `ON_CALL_DUTY`, `CALL_IN_WORK`, `TRAVEL_TIME` and the rest rules are untouched (refinement `:272`). `AbsenceRule.Evaluate` is **not retired**; it changes only in Do 5's default credit (R35).
5. **R35.** The 0-hour default credit and reduction become `DayNorm.ForWeekday(37.0m, fraction)`, keeping the 7.4 basis (7.4 × 5). This applies in `GetNormCreditHours`, `GetNormReductionHours` (or their core replacements) and `AbsenceRule.Evaluate`.
6. **Label each intentional change in the report** (refinement `:621-626`):
   - the line date moves from the period's first day to the week's Sunday;
   - 0.811 gives 30.00, not 30.007, and the 100% threshold is 32.45, not 32.44;
   - the multi-week total on a calendar month is 162.80, not 148;
   - a non-aligned legacy period is judged week by week (1–6 September norm 29.60).
