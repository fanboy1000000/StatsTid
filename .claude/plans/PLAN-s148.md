## Plain-language summary (read this first)

**What S148 is.** In S147 the owner decided how the state's agreements should be read (ADR-043): the norm is a calendar month, every hour above it is flex, and only hours a leader ordered become overtime. S148 does not yet change how anyone is paid. It does two things first. **Stage 0** removes the places where today's system pays or approves something it should not. **The config stage** makes the configuration editors' values the values payroll uses: each one dated, resolved for every day, and frozen into the month's proof, instead of payroll quietly using rules compiled into the code. The test that holds the sprint honest is easy to say: every demo payslip comes out the same before and after. The monthly norm, where payslips do change, is S149.

**The order it lands in, and why.**
0. **The pay pin, first and alone (wave 0).** Before anything changes, a test builds the two demo worlds, runs payroll on every month the demo approves, and stores the result as a fixed "golden" file. Docker does not run on the owner's machine, so the golden is captured by CI from code identical to the base. Every later checkpoint must reproduce it byte for byte.
1. **Stage 0's independent fixes (wave 1).** Payroll's "the same person signed twice" refusal gets its own name and comes before calculating; the old time-registration route goes, and payroll refuses any stored hour typed as something other than ordinary work; a day can no longer hold more paid absence than it was worth; overtime compensation refuses when its own guarded update refused; the orphan list stops counting a departed manager as cover; the editors say "does not yet affect pay"; two small pin sets.
2. **Skema's save path (wave 2).** The leftover "manual hours" retire; children's sick days follow the agreement texts per OK version, per illness, with the call-home day. This is the sprint's one change to pay arithmetic (a new credited code), so the evaluation marker moves once, to `weekly-timeline-v3`.
3. **The rest check (wave 3).** The 11-hour check reads the clock intervals employees type in Skema; the screen's instant warning and the server's check are proved to agree.
4. **The config stage's foundation (wave 4).** The schema (dated configs, the local profile's new settings, customary days, the HR facts, the dated organisation); two retirements; dated config reads; the dated organisation and the dated transfer; and the "pay inputs" lock on every Backend writer that dates a pay input into the past.
5. **Payroll joins (wave 5).** Transfers split a month in payroll; a past-dated publish lands the paid months it reaches on HR's worklist; one dated, fail-closed lookup; **the engine computes only with the configs it is handed (the moment the editors reach pay)**; configs frozen by value into each month's proof; and payroll's half of the lock, which refuses "calculate again" when an input changed during the recording.
6. **The editors (wave 6).** The local profile's new settings, customary days, the HR facts editor, the date field on the central editors.
7. **The demo (wave 7).** The demo world gains profiles, customs and HR facts with no pay effect; the pay pin runs a final time.

**Why the pay path moves in one place.** Today the screens and payroll read configuration differently, and payroll ignores the database entirely. If payroll were switched over piece by piece, there would be a moment when a payslip used one rule and the screen another. So every step before wave 5's engine switch (T14b) is invisible to pay, the switch is one merge, and the lock's payroll half (T24) follows it inside the same wave, so no checkpoint ever sees payroll reading dated configs without its "calculate again" check (`REF:786`).

The two copies are hand-written test databases whose tests save overrides, which from wave 4 always write a history row (NR-P28).

A Docker fact is "CI-pending" until a checkpoint run shows it green.

3. **File overlap is designed out by order, not by merge luck.** The table below lists every production file two tasks touch; each pair is in different waves or merges in a stated order, and each task touches only the lines named for it.
4. **Contract-changing backend tasks are stacked with their `ux` follow-up** (S146/S147's pattern): REGEN regenerates `docs/api/openapi.json` on the backend branch, the `ux` task branches from it and runs `npm run gen:api`, and the stack merges together, so master's `tsc` is never red between two merges.

A paired `-T` pass works on its implementer's branch after the implementer returns. No `git stash` anywhere.
6. **Inside a wave the later-merging task merges master before its gate** (rebuild, re-run its suites); a test file two `-T` passes in one wave both report is resolved by that rebuild, never by hand-merging assertions.
7. **The pay path's two halves stay inside one wave**: T14b (the engine switch) and T24 (payroll's recheck under the lock) both merge in wave 5, and no checkpoint runs between them (`REF:786`). CI-W5a runs before T14b; CI-W5 after T24.

1. **The mutation commit.** The re-spawned `test-qa` applies the run's mutations in a detached worktree. It runs Unit, DemoSeed and the non-Docker Regression facts there and records every fact that goes red. It then commits on a throwaway branch. *(NR-P31: the paired `-T` pass's own local run under the mutation, reported at its gate, is the first census; this re-run confirms it, and any difference between the two is recorded by name.)*
2. **The frozen list.** It is the pin's assertion (the row's "must trip" cell), plus every fact observed red in step 1, plus every Docker, smoke or e2e fact argued to go red, from any earlier wave. It is written in the mutation commit's message and copied to the sprint log before the push.
3. **The workflow patch.** The Orchestrator adds one commit on that branch only, "EVIDENCE ONLY — ci.yml continues past expected failures". It adds `if: ${{ !cancelled() }}` to exactly three `build-and-test` steps: "Run DemoSeed tests (QUAL-096)", "Apply init.sql to the services-postgres (schema + seeds for the :5432-coupled classes)" and "Run regression tests" (`.github/workflows/ci.yml:168`, `:178`, `:187`). Nothing else changes, and the job still ends red. *Why:* the "Run unit tests" step (`:165-166`) has no continuation and those three steps have no `if:`, so an expected Unit red would skip the Regression step and the Docker pin would never be observed; the patch reaches the run because the workflow triggers on `pull_request` to master (`:4-7`), which runs the PR's version of the workflow; the `test-results` upload already runs `if: always()` (`:199-204`). Master's CI is unchanged.
4. **Reading the run.** `gh run download <run> -n test-results`. The failed set is read from the Unit, DemoSeed and Regression trx files, the `smoke-test-results` artifact (`ci.yml:266-271`), the e2e job's report (uploaded only when e2e fails, `:386-393`) and the other jobs' conclusions (NR-P31). A run with no Regression trx is not evidence and is repeated.
5. **Judging.**
   - **A pin counts as proved only when its trx failure message is the row's "must trip" assertion** (NR-P29). A pin red at an earlier assertion (a setup or save step) is not evidence for the "must trip" cell: it is recorded as what actually tripped, and the row's evidence claim is narrowed to it.
   - The pin green is a finding: the pin does not discriminate, so fix the fact and re-run. A listed **non-pin** census fact green is a census over-claim, recorded by name, with no re-run (NR-P30).
   - An unlisted red is dispositioned by its assertion message. If the mutated behaviour explains it, it is recorded by name in the sprint log's mutation table as a census miss, with no re-run. If not, it is a defect and gets a fix task.
   - Mutations batched into one run stay independent of each other's pins.
