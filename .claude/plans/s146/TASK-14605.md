## Plain language — why

Today the next month's opening flex balance is whatever the caller sends, the engine's closing balance is checked and thrown away, and nothing records it. After this task each paid month's export record holds its opening and closing balance and where the opening came from; the next month opens from the previous month's recorded closing, through **one function** that every input goes through, computed before the calculation and re-checked under a per-employee lock inside the writing transaction; a correction updates the balances and names the next month when its closing moved; and a month that cannot be chained is refused by name, never silently opened at 0.

## Contract (the WHAT)

1. **The function** (R-14, transcribed — do not redesign — as amended by R-28: no `route` input; case 3a reads "M ∉ Records", because on the correction route M is always in Records at admission: the pre-check at `RetroactiveCorrectionService.cs:176-183` refuses an unrecorded month before PCS is called). A Payroll-local pure core, for example `FlexLedgerOpening.Derive`, over the terms of C2: *record* = any `payroll_export_records` row; *ledger record* = one with `opening_balance IS NOT NULL`; *S* = the earliest ledger month; *P* = M−1; `EmployedIn(X)` = `IsEmployedOn(Windows, d)` for any day d of calendar month X.

```
DeriveOpening(E, M)                                    // R-28: no `route` input
  precondition: M holds an EMPLOYED day of E (otherwise no flex is settled, no record is
                written, and the function is not called). Replay never calls it (R42).
  inputs:  Ledger  = E's ledger records as (month, opening, closing, provenance)
           Records = the months of E's records of any kind
           Windows = E's employment windows over [P.start, M.end]   // R-28: the function's own read
           S = min(Ledger.month) when Ledger is non-empty;  P = M − 1
  read twice with the SAME function: self-managed before the calculation (admission), and
  in-tx under the ledger lock for the recheck (records via a (conn, tx) overload of the
  export-record repository; windows via IEmploymentWindowResolverInTx).

  1. M ∈ Ledger and Ledger[M].provenance = LEDGER_START
        → (Ledger[M].opening, LEDGER_START)            // re-run and correction alike; a start is never re-derived
  2. Ledger is empty
        → (0, LEDGER_START)                             // the first month the system pays, whatever month it is;
                                                        // raw records do not count, so raw history never dead-ends
  3. M < S
     3a. M ∉ Records                                    // R-28: on the correction route M is always in Records
        → REFUSE 409 payroll-export-out-of-order, naming S
     3b. otherwise (M has a raw record: a re-run or a correction)
        → (0, UNTRACKED)                                // never stored: balances stay null; any FLEX_PAYOUT line
                                                        // is dropped; result and event say "flex not tracked:
                                                        // the month precedes the ledger start S"
  4. M > S   (M = S is always case 1)
     4a. EmployedIn(P) and P ∈ Ledger   → (Ledger[P].closing, CHAINED)
     4b. EmployedIn(P) and P ∉ Ledger   → REFUSE 409 payroll-prior-month-not-recorded, naming P
                                           ("export P first"; if P ∈ Records, "correct P first")
     4c. not EmployedIn(P)              → (0, REHIRE)
```

2. **PCS owns the derivation.** A ledger reader (Payroll-local `IFlexLedgerReader`, Postgres implementation over the export records, with a `(conn, tx)` read) is an **optional constructor dependency, never silent**: a calculation that reaches the function without one throws `InvalidOperationException` naming the registration, exactly like `:3608-3617`. Admission calls the function after the existing checks and before any rule call. **The windows are the function's own read over `[P.start, M.end]`** (R-28, R-36; at admission: the self-managed `IEmploymentWindowResolver.GetWindowsAsync`), never `histories.EmploymentWindows`, which `ReadPlanHistoriesAsync` reads over `[periodStart, periodEnd]` (`PeriodCalculationService.cs:3146`) and which `GetWindowsAsync` scopes to overlapping spells (`src/SharedKernel/StatsTid.SharedKernel/Interfaces/IEmploymentWindowResolver.cs:60-76`). **Without a registered resolver, `Windows` is null and every day counts as employed (`IsEmployedOn`, `:3481-3485`), unchanged; the chain then needs only P's ledger record** (R-37); a refusal throws a named exception (*Hint:* `FlexLedgerRefusalException` carrying the kind and the named month) mapped to 409 `{ success:false, error, kind, month }` on both routes. **The `decimal previousFlexBalance` parameter is retired** from every entry point above; the derived opening feeds the timeline call and `FreezePlanInputs`. Replay keeps the frozen opening (`:2230`) and copies the frozen provenance onto its result.
3. **The request field** (`Program.cs:829`, `:848`) becomes `decimal?`; a non-null value is refused with 400 `{ success:false, error, kind:"payroll-opening-balance-not-accepted" }` before any read, beside `RefuseBodyHours`.
4. **The result** (`PeriodCalculationResult`) carries opening, closing (the engine's clamped `NewBalance`) and provenance. Under `UNTRACKED` every `FLEX_PAYOUT` export line is dropped, the balance members are null, `FlexProvenance = "UNTRACKED"`, and the route response and the correction event say "flex not tracked: the month precedes the ledger start S" (R-14 3b). `PlanInputs.OpeningFlexProvenance` is frozen, so a replay reproduces the same result; it is **not** added to `IsComplete` (`PeriodCalculationService.cs:2253-2260`) (R-33 item 2).
5. **The ledger lock, every writer** (R-15). `ExportAsync` takes, as the **first statement** of its transaction (right after `:135`, before `:143`), one statement over the distinct employees of its groups:
   ```sql
   SELECT pg_advisory_xact_lock(k)
   FROM (SELECT DISTINCT hashtext('payroll-ledger-' || e) AS k FROM unnest(@employeeIds) AS e ORDER BY k) s;
   ```
   The correction takes the same lock (one employee) right after `RetroactiveCorrectionService.cs:302`, before `:307`. This covers all four routes; the raw routes write null balances and are otherwise unchanged.
6. **The under-lock recheck** (R-14). Inside the writing transaction, after the lock, the function runs again on in-tx reads (records through a new `(conn, tx)` overload that also returns the balances, reviewer c3 N4; windows through **the new in-tx range overload** over the same `[P.start, M.end]` (R-28, R-36), with `IEmploymentWindowResolverInTx` registered in the Payroll host — rewrite the `Program.cs:70-72` comment). **The overload (R-36, a declared cross-domain change):** `IEmploymentWindowResolverInTx` gains `GetWindowsAsync(NpgsqlConnection conn, NpgsqlTransaction tx, string employeeId, DateOnly from, DateOnly to, CancellationToken ct)`, and `EmploymentWindowResolver` implements it by the existing self-managed body with a `(conn, tx)` command through `ReadWindowRowAsync`, the inverted-range check included. About fifteen lines; no other change to either file. Report it as the ADR-040 D5 mirror. Not a per-day loop: the same function must run on in-tx reads (R-14), and under the ledger lock every round-trip would be held by every payroll writer for the employee. Proceed only on no refusal and the same **(opening, provenance)** the calculation used; otherwise 409 `payroll-ledger-changed` ("the previous month's balance changed; retry" / on the correction route "retry: the previous month's balance changed while this correction was computed"). A correction compares against **its own** calculation's pair, not M's recorded values. *Hint (HOW):* `PayrollExportContext` carries the expected pair; the export calls the function through the reader's in-tx surface.
7. **Write the balances.** A first export inserts opening, closing, provenance (`TryInsertRecordAsync`); a correction updates them beside `current_effective_lines`. **Zero-line month** (R-3): calculate-and-export writes the record whenever the plan holds an EMPLOYED day, even with no lines, passing an explicit (employee, year, month) identity to `ExportAsync`; the hash of an empty line set is defined once; a month with no EMPLOYED day writes none.
8. **The same-hash no-op** (R-16, `:208-221`) compares the derived (opening, provenance) and the computed closing with the recorded triple; any difference → the existing 409 `payroll-export-conflict` "the balance changed; use a correction". `UNTRACKED` against all-null recorded balances is equal, **ignoring the calculated closing**; the content-hash compare is unchanged.
9. **The correction.** Balances updated in its transaction; the event carries the opening used, the closing before and after, and the provenance; `RetroactiveCorrectionResult` carries the same. Under `UNTRACKED`, `FLEX_PAYOUT` is excluded from **both** sides of the diff and `FlexDelta` is null, so no flex correction line is emitted (reviewer c3 W4). A correction whose month lost every EMPLOYED day leaves the balances unchanged and its event says so (or refuse; your call, reported — reviewer c3 N7). A raw month after S fills its nulls when P is a ledger record (4a).
10. **C4.** `NextPeriodToRecalculateAsync` names M+1 when M's closing changed and M+1 is exported, **in addition to** the Sunday test (`:481`); comment the Sunday test as the F1 trigger the model program removes.
11. **Events and mappers.** `PayrollExportGenerated` carries opening, closing, provenance; the two mappers put the new members in `details` (omitted when null, as the S145 next-period keys are).
