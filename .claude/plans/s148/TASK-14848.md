## Plain language — why
- **Two readers.** Payroll and the compliance check read an employee's dated record (profile, organisation, agreement code) for one day through `EmploymentProfileResolver`. Since S148, Teamoversigt and the balance read the same records for a whole month through `DatedRecordTimeline`.
- **The divergence.** Where two **profile** rows cover the same day, the timeline takes the later start. The resolver's profile query has no `ORDER BY`, so which row it returns is undefined. FU-T's parity run returned POS-B from the timeline and POS-A from the resolver. Position, part-time fraction and employment category come from that row, so pay and the screens could disagree.
- **The fix.** The resolver's profile read takes the latest start among covering rows. Its own organisation sub-select, `UserAgreementCodeRepository.GetByUserIdAtAsync`, the profile endpoints' today read (`EmployeeProfileEndpoints.cs:1647`) and the approval screens' lateral reads (`ApprovalPeriodRepository.cs`) all already apply that rule.
- **Who notices.** Nobody today. No known writer creates overlapping profile rows: the database enforces one live row and unique start dates, not non-overlap. Unique start dates also mean the order has no ties.
