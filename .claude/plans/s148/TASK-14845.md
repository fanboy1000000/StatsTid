## Plain language — why

**The weakness (SEC-062).** Before a handler changes something about a person, it asks the scope validator: "may this administrator act on this person?" The validator answers from a read of the person's organisation, taken before the handler locks anything. If another administrator transfers the person to a different institution in that moment, the write still goes through, on a person the administrator was never checked for. *Example:* an HR officer scoped to Styrelse A opens "remove person" for P. In the same instant a colleague transfers P to Styrelse B. Today the removal still deactivates P, now an employee of B, whom the HR officer may not touch.

**Where the sprint stands.** TASK-14820 closed this on the user edit. TASK-14821, just before you, closes it on six more write handlers. A census of every scope check in the Backend (92 hits) found **22 more write sites** with a concrete case. Nine are in files S148 already changes. The other thirteen are in files no other S148 task touches, and the owner ruled on 2026-11-17 to fix them now too ("Fix all 13 now"), so **this one task closes the whole class**: one pattern, one review.

**The fix: one rule, three ways to get a value a transfer cannot move.** At each site the handler keeps the organisation the scope check approved (TASK-14821-S's sibling returns it). Once the handler holds a lock that a transfer must also wait for, it compares that organisation with the person's organisation as the lock found it. If they differ, it rolls back and answers **409, "refresh and retry"**, and nothing is written. What differs between sites is only where the stable value comes from (R2):
- **Tier 1, the reporting-tree lock is already held** (approve, reject, reopen, and four reporting-line writes plus remove person): a transfer takes the same lock, so the organisation the lock returned is stable. Nothing new to read or lock. The acting-manager DELETE takes that lock for the first time, in the same way the other reporting-line DELETE already does.
- **Tier 2, the person's row is already locked** (birth date, unit change): compare the locked row.
- **Tier 3, nothing stable today** (the send command, four overtime writes, the Skema save, four holiday-settlement and payout writes, the eligibility write, the worklist resolve): read the person's row with a lock, directly after the transaction's first lock, and compare before anything else. A refused request then learns nothing about the settlement or worklist rows of a person outside its scope.

**Who is never refused.** A manager or unit leader admitted only by their reporting edge never meets the guard on approve, reject or reopen: the guard fires only when the organisation-scope arm admitted the actor (R3). A person acting on their own data (sending their own month, their own overtime pre-approval, their own Skema) never meets it either (R2's self exemption). A GlobalAdmin, or an actor who is both HR over the old organisation and the person's manager, is refused once in a real race; a retry then succeeds, or meets the ordinary scope check.

**What it costs (R2, R3).** An HR save on someone else's Skema now holds that person's row for the length of the save, so an administrator's edit of the same person waits for it; a transfer waiting for that row holds the system-wide pay-inputs lock meanwhile, as the profile route already can. A dual-role actor gets one 409 in a rare race. Two more agent tasks in the sprint (73 become 75), and wave 5 starts one task later.

**Why not change the transfer instead (R2, option (b), declined).** Making the transfer take the per-employee lock would help only 6 of the 22 sites, would still need a compare at every one, and would change the transfer's lock order inside TASK-14821 with its deadlock freedom unproven. A row lock is enforced by the database; a plain read under an advisory holds only as long as every future writer remembers the advisory.

**What does not change.** No screen, no route shape, no pay figure. Every existing refusal keeps its body and its condition. The six heads and the user edit are TASK-14821's and TASK-14820's. The scope validator and the user repository are not edited.

**A second, smaller change (draft 3): nobody edits their own entitlement inputs.** S147 and S148 set a rule that nobody signs off a change to their own pay inputs: an HR user may not transfer themselves, change their own agreement code or profile, or close their own profile; a second administrator must ("P-26", built by TASK-14821). TASK-14821's security consult found two more doors, both in `EntitlementEligibilityEndpoints.cs`, which this task already edits: an HR user can set their own **entitlement eligibility** (today only the child's-sick-day entitlement, CHILD_SICK) and their own **birth date** (which decides when senior days start). On 2026-11-18 the owner extended the rule to both. So on these two routes, when the person acting is the person being changed, the request answers **403** with one fixed, date-free sentence and writes nothing, whatever the actor's role, a GlobalAdmin included. *Example:* an HR officer opens their own record in the edit drawer and corrects their birth date; that section's save fails with "a second administrator must perform this change", and a colleague makes the edit. *Why unconditional:* on P-26's other writers a save that changes nothing still succeeds, because the edit drawer re-sends a person's unchanged values on every save; neither of these two writers has a "nothing changed" outcome, and the drawer never sends either request unless the value changed, so there is nothing to let through. *What it costs (the owner accepted it with the option):* an institution with a single HR user needs another administrator to record that person's own birth date and eligibility. *Not changed:* the bare reversal of one's own settlement stays open and registered (SEC-065); editing anyone else's eligibility or birth date works as before.
