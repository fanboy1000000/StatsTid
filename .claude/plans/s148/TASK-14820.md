## Plain language — why

**The problem.** StatsTid knows which institution an employee belongs to today, but not which one they belonged to last March. The organisation is one live field on the person (`users.primary_org_id`, `init.sql:514`), and every dated read of an employee pastes today's value onto the historical day (`EmploymentProfileResolver.cs:167-179`, the column at `:173`). That was harmless while no institution's own setting reached pay. From wave 5 it does: each institution's local profile (its weekly norm, its flex cap) reaches the pay calculation. So recalculating a month from before a move would pay the old institution's days under the new institution's rules. The owner chose to date the organisation in this sprint (Q-1 = (a)). This is QUAL-206.

**What this task builds.**
- **A dated history of the organisation**, in the same shape the agreement code already has: one row per stretch of time, each with a start date and an end date.
- **A startup backfill**: every existing person gets a first row "from the start of history" (`0001-01-01`), so every past day has an organisation. The agreement code does the same today.
- **The user create** writes the new person's first row from `0001-01-01` too, not from the day they were created (NR-P7). *Why:* HR may later correct a new person's start date, profile and agreement code back to their real first day, and those days must already have an organisation.
- **The transfer gets a date.** When HR moves someone to another institution, the move has an "effective from" date. It is today when left out, it is never in the future, and it is never earlier than the start of the person's current organisation row (the last rule is a known, registered limit). A move dated after the current row's start closes that row and opens a new one. A move dated on the same day as the current row's start replaces the organisation on that row.
- **Nobody can transfer themselves.** A transfer changes whose rules apply to the person's own pay, and the owner's four-eyes rule from S147 says nobody signs off their own pay input.
- **A move dated into the past puts the paid months it reaches on HR's correction worklist**, and flags the settled holiday years it reaches, under a new reason, `ORGANISATION_TRANSFER`. Nothing is recalculated automatically.
- **Every dated read of an employee now gets the organisation of that day**, and fails loudly when a day has a profile but no organisation.

**Worked example.** *Ida works in Medarbejder- og Kompetencestyrelsen (STY01). On Tuesday 10 November 2026 HR records that she moved to Statens IT (STY02) from Monday 2 November 2026.*
- Before this task, one field says "STY02", and a recalculation of October uses STY02 for October.
- After it, her history holds two rows: STY01 from `0001-01-01` to 2 November, and STY02 from 2 November on. October resolves STY01, and November resolves STY02 from the 2nd.
- If November was already sent to payroll, November lands on HR's worklist with the reason "organisation transfer", dated 2 November.
- If HR then enters a second move, to Ekonomistyrelsen (STY03), also dated 2 November, the second row is changed in place. Ida still has two rows, the second now STY03.
- A move dated 26 October would be refused, naming 2 November, because it is earlier than her current row's start. That is the registered limit.

**What a manager and HR see.** Nothing about access changes. Who may see or edit a person keeps following today's organisation (`users.primary_org_id`), which the transfer still updates as it does today. The org-scope check never reads the dated history. A manager sees nothing new: no route serves the dated history in S148, and the transfer still closes the person's reporting lines and stand-in rows dated today, as it does now. HR of the new institution sees the person's earlier months, as today. The worklist rows and the audit rows are HR-only, as before.

**What does not change.** No screen, no route shape, no pay figure. The org-scope validator and the login token keep reading the live column. The transfer's reporting fan-out keeps its one "today". No payroll file changes: payroll's own organisation boundary is TASK-14822 (wave 5). PIN-1 holds, because the demo never transfers anyone, so every demo person resolves the same organisation as before (BC-12).
