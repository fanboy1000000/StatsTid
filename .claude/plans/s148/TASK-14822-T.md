## Plain language — why

**What TASK-14822 changes.** Payroll now reads each employee's transfer dates, so a move from one institution to another inside a month cuts the month there, using the existing "the employee's record changed" reason (`EmployeeProfileChange`). The same dates cut the opening week's days from the previous month and the institution's own profile lookup. A payroll service built without the new organisation reader refuses with a fixed message instead of planning without transfers.

**What you prove.**
1. **The split** (AC-C13a, the split half): a transfer dated Monday 15 June 2026 makes payroll calculate June in two parts, 1–14 and 15–30 June. Today it is one part, so the fact fails on today's code (F).
2. **Nothing already paid moves** (AC-C13b): when June has been exported and a transfer is then recorded back to 15 June, June's export record, lines and content hash stay exactly as they were. Nothing recalculates by itself. That already holds today, so the fact is a regression pin (R).
3. **A mis-wired service refuses** (AC-C13g): a service built without the reader refuses a month with the fixed wiring message. The reader is new, so the fact names something this sprint creates (N), and you prove it red by one named mutation, M-6, which makes the service skip the read instead.
4. **Two cuts nothing else sees** (AC-C13t, plan-added by A4 from TASK-14822's BC-5): an institution's profile that starts after the transfer splits the month there; and a transfer in the previous month's last days that this month settles cuts the context piece.
5. **The test tree keeps working.** Many tests build the payroll service by hand. Under TASK-14822's refusal each of them that plans would now refuse, so you hand each one a reader: a fake that answers "no transfers", declared with a comment, where the test is not about transfers (the prior-month reader's own precedent).

Expected values come from the plan and the briefs, never from what the code returns.
