## Plain language — why

**What goes wrong today.** HR can close a person's employment profile (the record of their part-time fraction and position) with the profile's delete button. The close ends the *profile*, not the *employment*: the person stays employed. Once that happens, nothing in the product can give them a new profile. The profile edit answers "not found" whenever no profile covers today (`EmployeeProfileEndpoints.cs:457-482`), and the only other writers of a profile row are creating the person (`AdminEndpoints.cs:1125`) and the start-up seeder, which since TASK-14849 deliberately leaves a closed profile alone (`EmployeeProfileSeeder.cs:98-104`). So from the close on, payroll refuses every month by name (QUAL-265: 422 `payroll-employment-record-gap`, "an HR administrator must repair the employment record"), and HR's "cannot register" list shows the person as "Skal rettes" (`FollowUpLists.tsx:554`), and neither can ever be resolved without editing the database. S141 saw this coming and left it "to a ruling" (`EmployeeProfileEndpoints.cs:450-456`). The owner ruled on 2026-11-24: build the repair now.

**What HR gets.** When no profile covers today, the same profile edit can **create a new profile from a date HR picks**. It is the ordinary profile write in every respect that matters: the same scope check, the same pay-inputs lock, one audit row, one event, the audit-projection row, the absence revaluation and the worklist hand-off. HR asks for a create explicitly (the header `If-None-Match: *`, "only if nothing is there"), so an ordinary edit sent from a stale screen can never silently bring back a profile a colleague closed on purpose. The profile read, which today just says "not found", now also says **whether a create is possible, from which date, and what the last profile held**, so the screen never offers something the server would refuse.

**What it must also get right.**
1. **Nobody re-creates their own profile.** The fraction and position decide one's own pay, so a self create answers 403 for every role, GlobalAdmin included (P-26; RES-003), before anything is read or locked.
2. **Only a real gap is repaired.** A create is refused (409) while any profile covers today, and while a profile is already scheduled to start later: that gap heals itself on its date, and HR must not "fix" it (the S141 rule, `hr-follow-up-process-register.md:394-396`).
3. **The new profile never overlaps the old one and always covers today** (BC-3). Its date is **today or earlier, and not before the day the last profile ended**. A date after today, or before that day, is refused with 400 naming the nearest date that works. Picking exactly the day the last profile ended leaves no gap at all; that is the screen's default (TASK-14852).
4. **A gap HR leaves is honest, not papered over.** A later date leaves the days in between with no profile (the ADR-020 D2 "gap-acknowledging" rule), and payroll keeps refusing the months they fall in. HR can fill such a gap afterwards with the ordinary edit, which inserts a row into a gap once a profile covers today (the router's case G; TASK-14851-T proves it).
5. **The same lock and the same hand-off as every profile change.** A create dated back into a month payroll has already recorded takes turns with payroll (the pay-inputs lock) and lists that month on HR's worklist.
6. **The "person moved while you were saving" guard** (SEC-062) answers 409 for a create exactly as it does for an edit.

**Worked example** (Anna, an HK employee of STY01, fraction 1.000, no position, her profile seeded from `0001-01-01`; Lise, LocalHR of STY01).
- *The close.* On **Monday 16 March 2026** Lise closes Anna's profile by mistake (`DELETE`, 204). Anna's only row is now `[0001-01-01, 2026-03-16)`. Anna stays employed. From that day payroll refuses March, and the "cannot register" list shows Anna, "Mangler dækning siden 16. marts 2026", "Skal rettes".
- *The read.* On **Friday 10 April 2026** Lise opens Anna. The profile GET answers **404** with `canCreate: true`, `uncoveredSince: 2026-03-16`, `earliestEffectiveFrom: 2026-03-16`, `scheduledFrom: null`, `lastPartTimeFraction: 1.000`, `lastPosition: null`.
- *The create, leaving a gap.* Lise creates from **Wednesday 25 March 2026**, fraction 0.800, position "Fuldmægtig", with `If-None-Match: *`. **200**: one new row `[2026-03-25, open)`, category taken from the closed row; one audit row `CREATED` (source `ADMIN_PROFILE_CREATE`, BC-5); one `users_audit` row; one `EmployeeProfileCreated` event with `EffectiveFrom` 2026-03-25 on `employee-profile-<Anna>`; one projection row targeting STY01; the body is Anna's profile as of today (0.800, "Fuldmægtig") with the new `ETag`. No worklist row (no recorded month from 25 March on). Anna leaves the "cannot register" list (a profile covers today).
- *What payroll then says.* **March 2026: still 422 `payroll-employment-record-gap`.** The days 16–24 March have no profile, and payroll refuses a month whose record stops covering a stretch of days (QUAL-265, `PeriodCalculationService.cs:4181-4190`). That is **QUAL-266's case**: the month is refused while the list no longer shows Anna, so nobody is pointed at it. **April 2026: paid, on 0.800** (its opening-week days, Monday 30 and Tuesday 31 March, are covered by the new row; `(unproven)` until AC-Q268h runs).
- *Filling the gap.* Lise then edits Anna dated **Monday 16 March 2026** (the ordinary edit, `If-Match`, fraction 1.000): the router inserts `[2026-03-16, 2026-03-25)` into the gap (case G, `TemporalWriteRouter.cs:215-221`), and March is then paid. `(unproven)` until AC-Q268h runs; it is the trace QUAL-266's row asks for ("Not traced: whether a profile PUT backdated over the gap can fill it once the later row exists").
- *The default, with no gap.* Had Lise kept the screen's default date, **Monday 16 March 2026**, the new row would be `[2026-03-16, open)` and March would be paid at once: 1–15 March on the old row, 16–31 March on the new one.
- *Refused.* A create dated **Friday 13 March 2026**: 400 `BEFORE_LAST_PROFILE_END`, `nearestValid` [2026-03-16]. A create dated **Wednesday 15 April 2026**: 400 `EFFECTIVE_FROM_NOT_TODAY_OR_PAST`, `nearestValid` [2026-04-10]. Lise re-creating her own profile: 403, nothing read further. A second create once Anna has a profile: 409. An ordinary edit (`If-Match`) sent from a tab opened before the close: 404, as today.
