## Plain language — why

**The problem.** The law (Arbejdstidsloven, EU directive 2003/88) says an employee must have at least 11 hours of rest between two working days. StatsTid checks that in two places: the server (the authority, which the manager's Teamoversigt also reads) and Skema's own instant warning while the employee types. Today the server's check is blind. It only measures rest from hours that carry clock times, and the hours Skema stores carry none: the clock times live in a separate table of work intervals (`work_time_projection`) that the check never reads. So every Skema day comes back "Hviletid ikke kontrolleret" (S147's interim notice), and a real breach is never reported to the manager.

**What this task changes.** The server's check reads the intervals. The Backend sends each day's intervals with the request, and the engine builds the working periods ("stints") from them alone. Two details matter:
- **Midnight.** Skema cannot hold 24:00, so a night shift is typed as 22:00–23:59 on one day and 00:00–06:00 on the next. Read literally, that is a one-minute "rest" at midnight. An interval ending at 23:59 or later and one starting at 00:00 the next day are therefore **one** shift.
- **Days not fully on the clock.** A day counts as checked only when its clock hours cover its project hours (to the hundredth). A day with more project hours than clock hours is still listed as "not checked" (the narrowed notice, owner ruling R-22): otherwise a day whose hours are not yet all on the clock would look compliant.

- **A rest across a month boundary.** A short rest from the last day of one month to the first of the next is reported once, in the month in which the rest ends, dated the earlier day. Today neither month's check reports it.

The hours checks (13 hours a day, 48 hours a week on average) keep reading the project hours, as ADR-043 D10 says: intervals give the time of day, project entries the hours. Two old single-check entry points that nothing in production calls retire.

**A worked example.** Mette works Tuesday 10 March 2026 from 22:00 to 06:00 and starts again on Wednesday at 16:00. She types Tuesday 22:00–23:59, Wednesday 00:00–06:00 and 16:00–20:00, with the matching project hours. *Today:* the server lists Tuesday and Wednesday as "not checked" and reports nothing; the screen warns her of a 0.02-hour rest at midnight. *After this task:* the server joins the two night halves into one shift ending Wednesday 06:00 and reports one daily-rest finding of 10 hours (06:00 to 16:00), which is a real breach. If she had not worked on Wednesday afternoon, there would be no finding at all.

**What does not change.** No pay figure: payroll never runs the rest rule (ADR-039 D5), and no payroll file changes (AC-S0-3e; PIN-1 at CI-W3). The engine still reads one compiled agreement config for the minimum rest (11 hours) until TASK-14826 (T14b) passes dated configs (A-11 is deferred there). No screen change: that is TASK-14814.

**ADR-039 D4, D5 and D5b — the continuous stint, the four checks' shapes, and the one-day widen** (`docs/knowledge-base/decisions/ADR-039-midnight-crossing-projection-normalization.md:58-110`). *Why:* the stint built from absolute instants is the model you keep; what changes is its source (intervals instead of timed entries) and the join (midnight continuity instead of a shared source id). The widen is why the request carries the day before the month.

~~~markdown
### D4 — Continuity link: the halves know they are one stint
The two projected halves carry a shared **source-stint identity** (the source event / outbox id). Without it,
the instant-based rest checks would misread the halves as two separate work periods. `TimeEntry` has no such
field today (`TimeEntry.cs`) — this ADR adds one to the projection row / consumed model.

### D5 — The four checks consume different shapes (they do NOT all want the split)
- **Hours-summing checks** — `CheckMaxDailyHours`, and `CheckWeeklyMaxHours` at segment edges — consume the
  **per-day normalized rows** (so post-midnight hours count on D+1 and route to the correct OK segment).
- **Rest checks** — `CheckDailyRest`, `CheckWeeklyRest` — evaluate the **continuous stint via absolute
  instants** (the TASK-1a instant reconstruction), NOT the blunt per-day split. A naive per-day split fed to
  the rest checks would manufacture a false 0-hour gap at midnight and a false extra "worked day".
  **Rationale-of-record correction (Step-5a):** the rest checks are safe under OK-segmentation NOT because of
  ADR-016's aligned-window/`RejectIfMultipleSegments` classification, but because **`PeriodCalculationService`
  never runs the rest checks at all** — `EvaluateSegmentAsync` calls only `/api/rules/evaluate`,
  `evaluate-absence`, `evaluate-flex`; `RestPeriodRule` runs ONLY via `/api/rules/check-compliance`, the
  UNSEGMENTED monthly compliance path, where the full continuous stint is present. (If a future change ever
  routes compliance through the planner, this assumption must be revisited — do not inherit the aligned-window
  reason.) The rest reconstruction must run BEFORE the in-rule period filter so a boundary crossing's pre-half
  still informs its stint's true start day (Step-5a BLOCKER — else weekly-rest falsely marks the period's
  first day as worked). The normalizer must also emit **rejoinable** halves even when the source
  `SourceStintId` is null (a deterministic shared id), else a caller-supplied crossing cannot be rejoined.

### D5b — Boundary fetch: no dropped hours at a period edge (Step-5a finding)
Because normalization moves a crossing's post-midnight half to `Date = D+1`, a crossing on the LAST day of a
queried period would have that half filtered out AND — since the immutable source row stays dated D — the
next period's fetch (keyed on `Date ≥ nextStart`) would never see it, dropping the hours from BOTH periods
(a payroll underpayment + the OK-version hours unjudged at the boundary). Therefore every calc/rule-input
fetch MUST include the prior day's boundary-crossing source rows (extend the fetch lower bound by one day),
normalize, THEN apply the period/segment filter — so each half lands in its owning period and nothing is
dropped. This applies at EVERY time-entry→rule-engine input boundary (D6); a boundary that does not normalize
must be a documented exclusion.
~~~
