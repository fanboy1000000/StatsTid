## Plain language — why

**The weakness (SEC-062).** Before a write handler changes a person's record, it asks the scope validator: "may this administrator touch this person?" The validator reads the person's organisation on its own database connection and answers yes or no. The handler then locks the person's row and writes. If another administrator's transfer moves the person to a different institution between the validator's read and the lock, the write lands on a person the administrator was never checked for.

**The fix has two parts.** TASK-14821 makes six handlers compare, under their lock, the organisation the check approved with the organisation the lock found, and refuse with 409 "refresh and retry" when they differ. (TASK-14820 already did this on the user edit.) To compare, a handler must know which organisation the check approved. Today it cannot: the validator returns only "allowed or not" and a reason. **This pass gives the validator two sibling methods that also return the organisation they authorised.**

**Why the validator supplies it, not the handler.** If the handler read the organisation itself, that would be a second read. A person moved A → B → A between the two reads would then pass the comparison (the lock finds A, the handler read A) even though the check approved B: the "double-transfer gap". Letting the validator report the organisation from its own single read means one read serves both the check and the comparison, so that gap is closed by construction (ruling 3). The validator also stays the only owner of its read: the active-only and the terminated-inclusive checks differ exactly in which read they use, so a caller-supplied user could be the wrong kind or stale.

**Why a separate pass.** `OrgScopeValidator.cs` belongs to the `security` agent's scope (`docs/AGENTS.md:30`). The paired-pass pattern keeps every agent inside its scope, with no exception granted, and the reviewers see your change together with TASK-14821's in one diff.

**What does not change.** Every existing caller keeps the same method, the same answer, the same reasons and the same log lines (ruling 5's census command prints 92 lines under `src/Backend` at `836a7b58`; three more callers sit in the Payroll host and the Orchestrator, Facts). Nothing reads the database more often, or in a different order.

**What was given up (ruling 3):** one more small pass to dispatch, and an additive change to a security-critical file with many call sites. The existing methods keep their signatures and delegate to one core, so no caller changes.
