## Plain language — why

**The problem.** StatsTid has three configuration editors: the agreement editor (GlobalAdmin), each institution's local profile editor (LocalAdmin), and the position-override page (LocalAdmin). An administrator who changes a value there reasonably expects it to change people's pay. Until wave 5 of this sprint it does not: payroll still calculates with rules compiled into the code and never reads these editors. The values do reach the screens and the booking checks. One more thing is not yet true either: the 11-hour rest check still reads its own built-in values too (`src/RuleEngine/StatsTid.RuleEngine.Api/Program.cs:134`). An editor that looks as if it changes pay, but silently does not, invites a wrong belief about someone's payslip.

**The decision (P-21, R-26).** For as long as it is true, each of the three editors says so, in one Danish sentence with this meaning: *"affects screens and booking; does not yet affect pay; the rest check still reads the built-in values"*. The label lives exactly as long as it is true. In wave 5, when the editors' values start reaching pay, TASK-14829 removes it in the same merge. That task keeps a small per-field note on the profile editor's two overtime fields, because those two still do not reach pay (NR-P13).

**What is left alone, and why.** The entitlement editor (part of the agreement editor page) and the wage-type mapping editor get no label. Entitlements are booking, and wage-type mappings already reach the payroll export, so the sentence would be false there.

**Who writes the words.** The Danish copy is yours. The meaning is fixed above.
