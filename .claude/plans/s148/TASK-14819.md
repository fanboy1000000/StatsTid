## Plain language — why

**The problem.** Until now StatsTid has known only which organisation an employee belongs to *today* (a single column on the user). S148 dates it (owner ruling Q-1 = (a)): TASK-14815 adds a table that says "this employee belonged to organisation A from this date", and from TASK-14820 on, every lookup of "what was true about this employee on day X" reads the organisation from that table, and **refuses loudly** when no row covers a day the employee's profile covers. That is the right behaviour for the product: payroll must never guess an institution.

**Why tests break.** The product writes the row itself: a user created through the product gets it from `0001-01-01`, and existing users get it from a start-up backfill (both TASK-14820). But about fifty test files create employees by writing rows straight into the database (a user, a profile, an agreement code), bypassing the product. Those employees would have no organisation row, and every one of their tests would fail the moment TASK-14820 lands, for a reason that has nothing to do with what the test checks.

**What this task does.** It adds the missing row **once**, in the shared test helper `RegressionSeed`, which about a hundred test files use, and, through one new small helper that writes only that row, in every test file that seeds employees by its own SQL: each row says "this employee belonged to their organisation from `0001-01-01`", the same anchor the product's own create and backfill use (NR-P7), so every day a test's profile can cover also has an organisation. **No test's expected value changes**, and no product code changes.

**Two more kinds of test the adjudication found** (rulings C1, C2):
- **Tests that create a user by SQL but give them a profile or an agreement code through the product** (a repository call or a route). They insert no profile row themselves, so the first census misses them; they get the row too.
- **Tests that delete their users when they finish.** The new table points at the user, and the database refuses to delete a user something still points at (a foreign key; there is deliberately no "delete the history too" rule, which would let history be erased to suit a test). Once a user has an organisation row, those clean-up deletes would fail. So each one first deletes the user's organisation rows, with the same condition.

**Why it waits for CI-W4a, and why it comes before TASK-14820.** The table exists only after TASK-14815, and CI-W4a is the run that shows the new schema, every test fixture and schema copy, and the dated configuration reads green in CI, where the database tests actually run. A sweep this wide, started on a schema not yet seen green, could not tell its own mistakes from the schema's. It lands before TASK-14820 so that no test is red between the two: the rows are inert until 14820's lookup starts reading them, and CI-W4 is where they are first proved (`REF:784`; `PLAN:64`).
