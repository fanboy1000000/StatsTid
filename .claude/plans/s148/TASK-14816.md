## Plain language — why

**Two pieces of configuration that do nothing are removed before the config stage builds on them.**

- **The "flex carryover maximum"** is a number an administrator can type in three editors (the agreement, a position override, an institution's local profile) and see in a fourth screen. **Nothing reads it**: the resolver copies it into the engine's config, and no rule looks at it (`REF:496`; ADR-017's own table says so, `ADR-017:246`). It also duplicates what the config stage adds properly: a plus cap with a test period (C-4). Keeping both would give a profile two plus caps. The owner chose to retire it, not reshape it (P-17).
- **`ValidateLocalOverride`** is a checker for the old per-key local settings. It has no caller in the product, it is marked obsolete, and the only thing it still does is keep its own tests alive (`ConfigResolutionService.cs:313-327`). The rule it guarded ("central rates cannot be changed locally") is now enforced by the profile's shape: a profile has no rate columns (`REF:492`).

**Worked example.** Today an HK administrator can set "Maks. flexoverførsel" to 80 hours on the local profile; it is saved, audited, shown back, and changes nothing anywhere. After this stack the field is gone from the database, the server, the events, the contracts and (TASK-14817) the screens. **No pay figure moves** (no rule ever read it; PIN-1 holds), and no other setting changes.

**One side effect to know.** Every calculation records a fingerprint of the configuration it used, a hash over every setting (`src/RuleEngine/StatsTid.RuleEngine.Api/Rules/ConfigFingerprint.cs:42-46`). One setting fewer means every fingerprint value changes. Nothing stored survives a reseed, and no test pins a literal fingerprint, so nothing breaks; a replay of a manifest recorded before this change would be refused by name (`replay-config-changed`), never recalculated silently.
