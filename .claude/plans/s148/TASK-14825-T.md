## Plain language — why

TASK-14825 makes the screens read each configuration "as it was on the day being shown", and makes them refuse rather than guess when the configuration cannot be read. It also lets the payroll service build that lookup, which the engine switch (T14b) will use. This pass proves it.

- **The payroll service builds** (AC-C1g). Today it cannot even start in development mode, because it registers a service whose ingredients it does not register (QUAL-184). A fact builds the host the strict way and fails if any registration is missing.
- **A failed read is an error, never a value from the code** (AC-C1m (1), its overtime half). *Example:* the configuration database is down at the moment an employee opens "my overtime compensation". Today the screen says "time off (afspadsering)", a value taken from the code, not from any decision. After TASK-14825 it answers "service unavailable", and a choice saved during the outage writes nothing.
- **The configuration seeds equal the code, read the way payroll will read them** (PIN-2). Before payroll switches from the compiled rules to the database (T14b), every compiled agreement, OK version and position must resolve, through the new lookup, to exactly the compiled values. Otherwise the switch could change a rate the demo never exercises.
- **The "before" timing for Teamoversigt** (N-3). The T14b stack will compute Teamoversigt's monthly norm day by day, which may be slower. This pass writes one timing fact that reads the team overview for a 30- and a 300-person team and prints the median of five reads. CI-W5a records it on the code just before T14b; TASK-14828-T re-runs the same fact for the "after" figure. A 300-person median that more than doubles, or exceeds 2 seconds, becomes a performance finding (NR-P3).
- **The tests that tested removed helpers.** TASK-14825 deleted the facts whose only subject was three retired helpers (QUAL-042). You check that nothing worth keeping went with them, and restore anything that did, pointed at the compiled table itself.
- **Each screen reads the day it shows, and refuses by name** (AC-C1o, B13). Five facts, each red on today's code: an agreement with no configuration is refused by name on the overtime screen and on the Skema month (the second proves the one Backend error mapping reaches a screen that asks the lookup only indirectly); the overtime model is the version in force on 1 January; and a Skema month shows each day's own norm when a central version, or an institution's local profile, starts on Monday 16 March 2026.
- **What the per-day reads cost** (B6). TASK-14825 resolves each day on its own (about 780 configuration reads for one year overview); one timing line records it at CI-W5a, so the registered limit has a figure.

### ADR-041's testing consequence (`docs/knowledge-base/decisions/ADR-041-copenhagen-business-day.md:64-76`)

~~~markdown
## Testing consequence — read this before writing a date test

**`WithFixedToday(DateOnly)` pins UTC midnight, the one instant where both calendars always agree.** A test built on it
passes under a correct *and* a broken implementation. It remains correct for tests whose subject is not the calendar.

A test whose subject **is** the business day must pin an exact instant where the calendars disagree, via
`WithFixedInstant(DateTimeOffset)` and the shared anchors in `BoundaryInstants` — and must assert **literal** expected
values. *A test that computes its expectation by calling the helper under test proves only that the helper agrees with
itself*; S142 found three such tests and deleted the shape.

**On a developer machine in Denmark, a frontend date test is vacuous unless it forces a non-Danish zone**, because the
browser-local day and the Danish day are the same day there. Force the zone, and assert that the forcing worked.

~~~
