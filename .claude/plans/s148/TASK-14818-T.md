## Plain language — why

TASK-14818 gives every agreement configuration and position override an "applies from" date, keeps every published version, and adds one read that answers "which version was in force on day X?". This pass proves it, and repairs the tests its new method signatures broke.

It proves, with facts that run against a real database in CI:
- **the date rules:** an empty date means today in Danish time; a future date is refused with today as the suggestion; a weekly-norm change dated mid-week is refused with the two nearest Mondays; a date before the version it replaces is refused with that version's date as the suggestion (AC-C2q); each publish's audit row records its date;
- **the read:** an archived draft that was never published never applies and never blocks a later date; two publishes on one day resolve to the one that took effect last, even when its transaction started first; every seeded configuration is in force from `0001-01-01`;
- **the override history:** after an edit, a switch-off and a switch-on, each day before the change still reads the old state;
- **the archive refusal:** archiving the active configuration answers 409 and writes nothing;
- **the planner:** a version starting on Monday 16 March 2026 splits March at the 16th; and when a version starts on the very day an employee changes agreement or position, the record keeps naming that change, not the configuration. Neither planning call writes a row anywhere (QUAL-182's no-write rule, asserted inside both facts). The planner is reached directly, because the payroll service is handed the dated tables only in wave 5 (DV-8).

**An example of why the history matters.** A flex cap of 100 hours is raised to 120 from Monday 2 November 2026. A recalculation of October in December must still use 100 on Friday 30 October. Without the history table the only stored row says 120, and October would be recalculated wrongly; the fact `CapEditedFromMonday2November2026_Friday30OctoberReads100_2NovemberReads120` holds that line.

**Mutations.** A fact that names something this sprint creates cannot fail on old code (it would not compile), so its red is shown by breaking the new behaviour on purpose ("a mutation") and watching the fact fail. Docker facts can only run in CI, so seven such mutations run in CI evidence runs after wave 4 (CI-M4a, CI-M4b); this pass writes the facts so that each one fails for exactly its own mutation, runs each mutation locally on the suites that do run here, and lists what each one should turn red.
