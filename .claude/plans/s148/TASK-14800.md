## Plain language — why

**What the pin is.** The owner's promise for this sprint is short: *every demo payslip comes out the same before and after*. S148 rebuilds how configuration reaches payroll, but it must not change anyone's pay; the pay changes come in S149. To hold the sprint to that promise there has to be a "before" to compare against, and today there is none: the demo never runs payroll, and the database is rebuilt from scratch rather than upgraded ("reseed, don't migrate"), so no old payslips survive. This task builds the "before".

A test creates the two demo worlds with the project's own demo generator, loads them through the same API calls the demo loader makes (time registered in Skema, each month sent by one person and approved by another), sends every approved month to payroll, and writes what payroll produced as one fixed text per world. That text is the **golden**: an expected output, committed to the repository once, that every later checkpoint must reproduce byte for byte. If a later change moves a single hour or krone on a demo payslip, the pin turns red.

**Why first and alone.** The golden must come from code identical to the sprint's starting point. If any other change merged first, its effect would be baked into the "before" and could never be seen. Docker does not run on the owner's machine, so the golden cannot be produced locally. Instead the test is built to fail on purpose while the golden file does not exist yet, printing the whole text in its failure message; CI keeps that message in its stored test results (checkpoint CI-W0); the Orchestrator copies the text unchanged into the two golden files (item O-1); a second CI run shows the pin green (CI-W0b). Only then may wave 1 merge.

**Why it must be able to fail.** A pin that cannot fail measures nothing, and the first design of this one could not: its demo months could not be calculated at all, which would have produced an empty golden that passes forever. Three things keep it honest. (1) *Non-vacuity rules* ("the test is not empty"): each world must hold at least three approved months; every approved month must be paid and produce at least one pay line; the number paid must equal the number the loader approved. (2) *PIN-1b* breaks the text-maker on purpose (it leaves out the amount, then the period end) and shows the comparison notices. (3) *PIN-2* covers what the narrow demo cannot see: the configuration rows in the database must equal the rules compiled into the code, so that when payroll switches to reading the database (wave 5) no rate the demo never touches can change silently.

**What the "seed" is.** The demo generator is a repeatable random world-builder: the same seed, size and date always give the same world, byte for byte. At the small ("smoke", about 30 people) size the default seed gives only about two approved months, too few to trust. So this task tries seeds 43, 44, … 142 for each world and pins the first one that holds at least three approved months, with a test that proves it is the first. *Chosen over* the large demo world (about 3,350 people), which makes the same point at many times the CI time; the large world is used only for a world no seed in the range satisfies. *Given up:* nothing of substance; a different but equally fixed small world.

**Golden, in one sentence:** a recorded expected result, captured once from known-good code and never regenerated, that later runs must match exactly.

~~~markdown
### D10 — Segment manifest: event-sourced + indexed projection

`SegmentManifest` is a record type in SharedKernel (not the same shape as `PlannedCalculation`); built from a `PlannedCalculation` via a mapping ctor.

**Event**: `SegmentManifestCreated` registered in `EventSerializer` (event count 43 → 44; DEP-003 update). `manifest_id` = event `Id`. (D10 amendment 2026-04-30: original spec said 34 → 35 based on a stale ADR-016 draft; the registry had grown across S6/S9/S12/S14/S15/S16/S17 to 43 entries by S20 dispatch — TASK-2007 verification confirmed 43 → 44.)

**Projection** in PostgreSQL: new table `segment_manifests`:
- `manifest_id UUID PRIMARY KEY`, `period_start DATE NOT NULL`, `period_end DATE NOT NULL`, `employee_id TEXT NOT NULL`, `calculation_kind TEXT NOT NULL` (`forward-calc` / `retroactive-correction` / `replay`), `boundary_cause_summary TEXT[] NOT NULL` (deduped), `created_at TIMESTAMPTZ NOT NULL`, `segments_jsonb JSONB NOT NULL`.
- Indexes: `(employee_id, period_start)`; GIN on `boundary_cause_summary`.
- Rebuildable from events.

**D10 amendment 2026-05-01** (during Phase 3 wave 1 review): `employee_id` column type and `SegmentManifest.EmployeeId` / `PlannedCalculation.EmployeeId` / `SegmentManifestCreated.EmployeeId` field types changed from `UUID` / `Guid` to `TEXT` / `string` to align with the rest of the schema (every other employee-id column in `init.sql` — `users.user_id`, `time_entries.employee_id`, `payroll_export_lines.employee_id` (in-memory), etc. — is `TEXT`/`string`). The original D10 spec wrote `UUID` without surfacing the schema-wide `TEXT` convention. Phase 3 wave 1 Reviewer flagged the divergence: the Payroll agent's TASK-2008 implementation had to synthesize a SHA-256-derived UUID for non-Guid string ids (e.g. `"emp-1"` test fixtures), which created an audit-cliff where `segment_manifests.employee_id` could never join to any other employee-keyed table without re-running the same derivation. Fix is forward-only: amend `init.sql` schema (no migration needed since no production DB yet exists with this table), amend SharedKernel Segmentation types, drop the SHA-256 derivation, drop the `::uuid` cast in TASK-2011's projection-rebuild SQL.

**Linkage** (amended 2026-04-29 during Phase 1 — `payroll_export_lines` is an in-memory C# model, not a persisted DB table; original D10 spec wrongly assumed DB-side per-line linkage. The audit chain below covers the same need without inventing new persistence.):
- `CalculationResult.ManifestId Guid` (additive; PAT-006 amendment) — in-memory + event payload.
- `audit_log.payload_jsonb` calculation entries carry `manifest_id` — additive, queryable.
- SLS export file format carries per-line OK-version stamping in file content (TASK-2010) — file-side, not DB-side.
- `segment_manifests` projection (queryable manifest history) joined to `audit_log` via `manifest_id` is the audit query path; per-line DB persistence of export lines is explicitly out of scope and recorded as a deferred question (revisit if/when product needs query-by-line history).

**Replay**: `PeriodCalculationService.ReplayAsync(Guid manifestId, CancellationToken)` returns a `CalculationResult` with the **same** `ManifestId` (replay does NOT mint a new manifest). **FAIL-006 — a tool whose failures are warnings is a tool that reports success** (`docs/knowledge-base/failures/FAIL-006-warnings-that-never-reach-the-exit-code.md`). *Why it matters here:* it is the DemoSeed loader's own failure record, and the pin is an oracle over that loader's world.
~~~

~~~markdown
## What happened

`tools/StatsTid.DemoSeed` recorded every failed period submit as a **warning**. Warnings were printed,
never counted, and never reached the exit code — the program returned **0** regardless. Combined with
S127's new allocation gate, the loader would have failed **374 of 375** sends and still exited clean.

A rerun made it worse: any `409` is treated as an idempotent skip, so a second run over a broken world
looked *identical* to a second run over a healthy one.

## Why the obvious fix is only half a fix

Routing the failure into the exit code catches a loader that *knows* it failed. It does nothing for a
loader that is wrong about what success means — wrong month, wrong status, row silently absent.

**Both halves are required:**

1. **Failures reach the exit code.** A distinct non-zero code, with the failing items listed.
2. **The outcome is asserted against an independent oracle** — here, the database, keyed on the natural
   key `(employee_id, period_start, period_end)`, with per-status counts derived from the manifest. Not
   the tool's own report of what it did.

Then **break the world on purpose and watch both go red.** In S127 that meant deleting one period row and
perturbing one day's hours so the loader's own repair path could not mask it: exit 6, verification FAILED,
and the failing row named. Under the old counters that run was byte-identical to a healthy one.

## The part worth remembering

**One of the four falsification attempts did not fire** — and that was the most useful result of the
exercise. It revealed that the "stray period" arm only sees employees the manifest names, a real scope
limit in a check written minutes earlier. It is now documented in the code rather than glossed.

A probe that fails to fire is not a wasted probe. It is the only way to discover that a check is narrower
than its name.

## Checklist for any load/migration/seed tool

- [ ] Every failure path increments a counter that reaches a **distinct non-zero exit code**
- [ ] Verification asserts against an **independent** source of truth, on a natural key — not the tool's
      own log
- [ ] Counts are **derived from the input manifest**, so "produced nothing" cannot pass
- [ ] Assert the **negative** too: no row where the manifest says there should be none
- [ ] Run the verification on a **fresh load AND a rerun** — idempotent-skip paths are where masking lives
- [ ] Break the world deliberately; confirm **every** arm fires; document any arm that does not
~~~
