## Plain language — why

**The label.** Since wave 1 the agreement editor, the position-override page and the local-profile editor carry a note: "the settings here affect screens and booking, but not yet pay; the rest check still reads the built-in values" (TASK-14807; S0-8). It was true until now. The T14b stack makes these values reach payroll and the rest check, so in **the same merge** the note goes (R-26: "the label is never false"). Leaving it would tell an administrator their edit does nothing to pay, when it now does.

**Two fields where it stays true.** The local-profile editor's **overtime ceiling** ("Maks. overarbejde pr periode") and **pre-approval** ("Overarbejde kræver forhåndsgodkendelse") are read by one thing only, the overtime-governance warning, and that warning still uses the agreement's built-in values (a registered legacy path, R-8, until stage 2). So these two fields keep a note of their own (NR-P13: "a statement that stays true is not removed").

**Skema's instant rest warning.** The day panel warns, while the employee types, when a work end has less than the minimum unbroken rest in the 24 hours before it. Today the minimum is a fixed 11 hours in the screen's code (`useSkema.ts:691`). The Skema month now serves the minimum in force for each day (TASK-14828), so an agreement whose minimum is 12 hours warns at 11.5 hours, as the server's check does.

**Worked example (AC-S0-4c).** An administrator publishes a 12-hour minimum rest from Monday 16 March 2026; the month serves 11 for Sunday 15 March and 12 for Monday 16 March. Mette types Sunday 15 March 10:00–20:30 and Monday 16 March 08:00–14:00. The Monday work ends at 14:00 after 11.5 hours of unbroken rest (20:30–08:00): **the panel warns** ("… kun 11,5 timers sammenhængende hvile …", with the minimum of 12). A Sunday work end with the same 11.5 hours is judged against Sunday's 11 and **does not warn**. Each work end is judged by the value in force on its own date (RR-7), exactly as the engine judges it (TASK-14826).
