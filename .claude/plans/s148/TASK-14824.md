## Plain language — why

HR's follow-up page has a "correction worklist": each row is a month already sent to payroll (or a settled holiday year) that a later change may have made stale, and under it a line per change that touched it, saying **why** in Danish: "Profilændring — effektiv fra 5.3.2026, tilføjet … af …". S148 adds three new reasons, and today the page does not know them, so it shows the raw English code instead:
- **`CONFIG_PUBLISHED`** (TASK-14823): an agreement configuration, a position override or an institution's local profile changed from a date that reaches the month;
- **`ORGANISATION_TRANSFER`** (TASK-14820, merged): the employee moved to another organisation from a date that reaches the month;
- **`EMPLOYMENT_WINDOW_CHANGE`** (TASK-14821, merged): the employee's employment start or end date moved.

**Worked example.** A GlobalAdmin publishes a change to HK's OK24 values dated Monday 5 January 2026, and January–April 2026 are on the worklist for an employee. Today each row's line reads "CONFIG_PUBLISHED — effektiv fra 5.1.2026, tilføjet …"; after this task it reads "Konfigurationsændring — effektiv fra 5.1.2026, tilføjet …". Nothing else on the page changes.

**Why these three words (A10).** Each label names the fact that changed, as its four siblings do ("Profilændring", "Overenskomstkode-ændring"): a configuration, the organisation, the employment period. The third is "Ansættelsesperiode-ændring", not "Ansættelsesdato-ændring", because the screens use "ansættelsesdato" for the **start** date only (`EntitlementSection.tsx:85`, `PersonDrawer.tsx:804`) and "fratrædelsesdato" for the end date (`TerminationPage.tsx:219`, `:302`); the trigger covers both, so a label naming the start date would tell HR the wrong date moved when an end date is corrected. Given up: the drawer's own verb for a move, "overflytning".

**What does not change.** No request, no response, no layout, no other label, no action. The rest of the line (the date, who and when) and every existing label stay as they are.
