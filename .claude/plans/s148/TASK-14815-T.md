## Plain language — why

TASK-14815 adds columns, tables and five new events to the database and the code. Three kinds of test can quietly fall behind such a change, and this pass catches each:

1. **The new events must read back exactly.** Every event is stored as JSON and read back when the history is replayed. If a member is misspelt, left out of the serializer's list, or made "required" while it can be empty, an old event can no longer be read: the audit trail breaks. You write one fact per new event that writes it with every member filled, reads it back, compares member by member, and checks the exact name each member is stored under (DEP-003; ruling A5).
2. **Hand-written test databases.** Some tests do not build their database from `init.sql`; they carry their own copy of a table. A copy that lacks the new mandatory "applies from" column breaks every test that saves a config through the real code. That was S144's one defect after its close (a copy whose default hid a mandatory column, `docs/operations/model-routing-register.md:125`). You bring each copy into line with `init.sql`.
3. **SQL fixtures.** Tests that insert a config row by hand must now say from when it applies; otherwise the insert fails, and a test that expected a *different* failure would fail for the wrong reason (example below).
4. **The new audit mappers must point at the right institution** (ruling A6). Each new event has a small "mapper" that turns it into a row of the audit screen, and that row carries the organisation whose administrators may see it. A wrong organisation would show the row to the wrong institution, and the writers that would otherwise test this may not arrive in S148 (customary days are cuttable, C-10). So you write one small fact per mapper now.

**Worked example.** `S122CompensationVocabularyTests` inserts an agreement config with the forbidden compensation value `PAYOUT` and expects the database to refuse it *by the named check* (`…/Config/S122CompensationVocabularyTests.cs:79-89`). After TASK-14815 the same insert lacks `applies_from`, so PostgreSQL refuses it one step earlier for a missing value (23502, not 23514), and the fact goes red although the check still works. Supplying the date puts the fact back on what it is for.

Expected values come from the plan and this brief, never from what the code returns.
