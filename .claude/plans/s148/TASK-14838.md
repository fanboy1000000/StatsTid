## Plain language — why

**Since wave 5 the central editors' values reach pay**, each from a dated version: an agreement configuration applies from the day its publish names, and a position override from the day each write names (QUAL-182, ADR-043 D12). The server has enforced the date rules since wave 4: never in the future, never before the version it replaces, and a Monday when a field the weekly calculation reads changes (`AppliesFromValidation.cs:6-23`). **The screens never caught up**: they send no date (so every write means "today"), never show a version's date, and on a mid-week refusal show the server's English text. Until this task, four actions are simply refused on any day but a Monday (the interim the owner was told, O-12 (7), `PLAN:763`; it ends at your merge). This task makes the screens match the server, under the rule wave 6 ends with: **a screen never offers an action the server refuses.**

**What changes, screen by screen.**
1. **The agreement editor** (GlobalAdmin, `/global/overenskomster/:configId`): the publish asks "applies from" (today by default; no later day offered; no day before the newest published version's date, read from the configuration's version list, ruling 30); a published version shows its date; an active configuration no longer offers "Arkiver" (the server answers 409 since wave 4: "publish a successor", NR-15), a draft still does; and **every label is tied to its field** (N-7, your first commit), so a screen reader names each input.
2. **The position-override page** (`/lokal/stillingstilpasninger`): create, edit, switch off and switch on each carry a date with the same limits, and each row shows its date. **A local administrator** reaches the page (it lists the overrides for them) but the server lets only a central administrator change anything (SEC-032); so a local administrator now sees the list **without** "Opret ny", "Rediger", "Deaktiver" and "Aktiver", and one note saying only a central administrator can change them (ruling 31).
3. **A refusal is never a dead end** (NR-P14, NR-P17). When the server refuses a mid-week date because a week-read field changed, the editor offers the Mondays the server would accept: on or before today, and on or after the newest version's date. **When two qualify, both are offered, in date order** (ruling 29: the server names both, and choosing one would guess the administrator's intent). If none exists, it says which Monday is the earliest possible date. Every other error shows as it does today (ruling 33).

*The edit-person drawer (NR-P4, X7) was this task's in draft 1; it is TASK-14850's from the split (ruling 28).*

**Worked example (AC-C2b (2), case (b)).** The newest published version of HK/OK26 applies from Tuesday 10 November 2026; today is Thursday 12 November 2026. A GlobalAdmin publishes a draft that changes the weekly norm, dated today. The server refuses: "not a Monday", listing Monday 9 November and Monday 16 November (`LocalAgreementProfile.cs:134-148`). The 9th is before the newest version (the server would refuse it again, as `BEFORE_PREDECESSOR`); the 16th is after today (refused as a future date). So the editor offers no date and says the earliest possible date is Monday 16 November 2026. *Case (a):* with the newest version from Monday 2 November 2026 and the same refusal for Wednesday 11 November, the editor offers Monday 9 November 2026. *Two Mondays (ruling 29):* with the newest version from Monday 2 November 2026 and a refused date Tuesday 3 November 2026, the server names Monday 2 and Monday 9 November; both are on or before today and on or after the newest version, so the editor offers both, Monday 2 November first.
