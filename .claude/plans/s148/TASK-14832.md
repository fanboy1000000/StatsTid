## Plain language — why

**What an institution gets.** Since wave 4 the local profile table has eighteen new columns: an institution's own flex rules (the period flex is settled over, the period the cap is tested over, a plus cap, a minus cap, a daily credit cap, what happens to hours above the cap, what happens to a leaver's balance), office hours as a clock window per weekday, and the basis on which a day of paid absence is credited (ADR-043 D2, D3, D6). Nothing can fill them yet: the save route ignores them, and the repository neither writes nor reads them. This task makes the save accept them, check them, store them, read them back and record them in the audit trail. **No pay changes:** no calculation reads these settings in S148 (`REF:35`); stage 1 (S149) does.

**Three things it must also get right.**
1. **Bad values are refused at the door (SEC-061).** Today a LocalAdmin can store a weekly norm of 0 or −5 hours, or a negative flex or overtime maximum, and since wave 5 the weekly norm and the flex cap on a profile reach pay. This task checks the old fields and the new ones before anything is locked or written. A refusal is the route's existing 400 with a per-field list (at most one error per field), and nothing is stored. No value has an invented upper ceiling (SEC-033, owner ruling OQ-2). The only limit is the column's own: a number with a third decimal, or too large for its column, is refused with a 400 instead of reaching the database, where today the first is silently rounded and the second fails as a 500 (ruling 4). The same goes for a misspelled option, a weekday with only a start or only an end, and a clock time with seconds.
2. **A save that changes only a new setting is never dropped (the comparator).** A same-day save that changes nothing is a deliberate "no-op": no new version, no audit row, no event. The check that decides "nothing changed" looks at the four old fields only, so a save that changed only, say, the plus cap would be judged "nothing changed" and silently discarded. It must compare all twenty-two settable columns, and the audit delta must name the same twenty-two, so the two can never disagree.
3. **The concurrency protections stay exactly as wave 5 left them.** The save takes the system-wide "pay inputs" lock first, runs at READ COMMITTED, and refuses with 412 when the profile it locks is not the one it read before waiting (A9). This task does not touch those lines.

**Worked example.** STY01's HK/OK24 profile R is open from Monday 2 March 2026 at version 3, with no plus cap. On Thursday 5 March 2026 a LocalAdmin sets the plus cap to 37 hours and saves with the same date (`If-Match: "3"`).
- *Today:* the route ignores `flexPlusCapHours`; the comparator sees four unchanged fields and the route answers 200 at version 3, with no row change, no audit row and no event. The 37 hours vanish without a word.
- *After this task:* the value passes the check (≥ 0). Under the lock the repository finds the same profile (A9 passes) and the same date (an edit in place) with one changed column, so it updates the row to **version 4**. One **`MODIFIED`** audit row is written whose delta is `{"FlexPlusCapHours":{"Old":null,"New":37}}`. One **`LocalAgreementProfileChanged`** event goes to the outbox on stream `local-agreement-profile-STY01-HK-OK24` with the same `ChangedFields` and `PrecedingProfileId` null (an edit in place keeps the profile id). Last before the commit, any already-paid month of STY01's HK employees from 2 March onwards goes on HR's correction worklist under `CONFIG_PUBLISHED` (TASK-14823's hand-off). That happens even though no S148 calculation reads the plus cap, by design (`REF:447`: the list must not change meaning stage by stage). The response and a later GET show `flexPlusCapHours: 37`.
- *Had the cap been −1:* 400, `fields: [{ "field": "FlexPlusCapHours", "code": "MUST_NOT_BE_NEGATIVE", "nearestValid": null }]` under `error: "Profile validation failed"` (ruling 4's code; ruling 5's text), answered before the lock; nothing written.

**What it costs.** Nothing at run time worth naming. One existing behaviour gains weight: the save replaces the whole profile, so a client that sends only the old five keys stores "not set" for the eighteen new settings (BC-9; ruled to stay, ruling 8). The one client, the profile editor, sends every field from TASK-14833 on.

**What does not change.** No route, policy, event type, audit action, table, lock or isolation level; no pay figure; the existing refusals (403, 428, 400, 412) keep their conditions and order, and their bodies except one text: the `error` of the future-date 400 and of step 5's 400 becomes `Profile validation failed` (ruling 5), because "alignment" would be false for a negative cap.
