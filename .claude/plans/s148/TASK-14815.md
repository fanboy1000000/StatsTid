## Plain language — why

**The problem.** From wave 5 on, payroll will pay each day with the configuration that was in force *that day*, and it will freeze those values into the month's proof (ADR-043 D12). Today the database cannot even say what "that day" means: an agreement config and a position override have no date from which they apply (only a `published_at` time stamp, `init.sql:1394`), an override is edited in place so its old values vanish, and an employee's institution is one live field (`users.primary_org_id`, `init.sql:514`), so "where did Anna work last March?" has no answer.

**What this task does.** It builds the storage only, no behaviour:
- a mandatory "applies from" date on agreement configs and position overrides; the seeded rows get the history-covering date `0001-01-01`, so they mean exactly what they mean today ("in force since always");
- a history table beside the override, so an edit no longer destroys the old values (NR-P8);
- the local profile's new settings (settlement period, caps, office hours, the paid-absence credit basis), empty for everyone;
- a table for an institution's customary days, a table for the two facts HR records about a person, and a dated table of which organisation a user belongs to;
- the five new events those tables' writers will emit, each registered so it can be read back (DEP-003) and each with its audit mapper, registered with its marker so the audit screen's backfill can see it.

**Every new date column is mandatory and has no default** (ruling A4). A writer that forgets a date must fail at once, not silently mean "in force since always": a default that hid a missing date was S144's defect after its close.

**Worked example.** *HK's flex cap is raised from 100 to 120 hours from Monday 2 November 2026.* Today the override row is overwritten: a recalculation of October would read 120. After this task the database has a place for both facts (a version applying from `0001-01-01` with 100, and one from 2 November with 120); TASK-14818 writes and reads them. *Anna moves from STY02 to STY03 on Monday 15 June 2026.* Today only "STY03" survives; after this task `user_organisations` can hold both rows; TASK-14820 writes them.

**What does not change.** No screen, no route, no pay figure, no read. Every new column is either nullable or carries the seeds' `0001-01-01`; every new table is empty except the override history's four seed rows. PIN-1 holds.
