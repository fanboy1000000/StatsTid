## Plain language — why

TASK-14842 changes how a missing holiday-balance record is created. Today a record created "late" forgets every day already booked (it starts at 0 used), the profile recalculation gives it a total of 0, and the year-end carryover gives next year the closing year's total. After 14842 a created record starts at the sum of the days actually booked for that type and year, and its total is the entitlement in force on the first day of its own holiday year.

This pass proves it with five facts, one per acceptance criterion: a booking, a reduction, a profile recalculation and a year-end carryover, each on a missing record; and one fact that an **existing** record is never re-counted. Several cases are built to fail for the likely *wrong* fix too, not only for today's code: a total taken from today's configuration (27) or from the closing year (25) instead of the year's first day (26). Then it checks every existing test that leaves booked days without a balance record, and re-pins only what the owner's rulings require. Expected values come from the addendum (pasted in TASK-14842's brief), never from what the code returns.

~~~markdown
## The rule

**A transaction whose first statement is a blocking advisory-lock acquire must pin
`IsolationLevel.ReadCommitted` explicitly — never the default overload.**

`pg_advisory_xact_lock` blocks until granted. Under REPEATABLE READ the transaction snapshot is taken
**before** the lock is granted, so the winner's commit — *the exact thing the loser was waiting for* —
stays invisible, and the loser proceeds on pre-lock state. The lock serializes execution while the
snapshot silently un-serializes the data, which is the worst of both.

## Checklist

- [ ] Advisory lock is the **first** statement in the transaction
- [ ] `BeginTransactionAsync(IsolationLevel.ReadCommitted, ct)` — explicit, with a comment saying why
- [ ] No memoized/snapshot-bound authority context is passed on this transaction
- [ ] Where two paths take advisory locks, they take **the same** lock in **the same** order — two locks
      acquired in different orders by two paths is a deadlock
- [ ] A test asserts the post-lock read **sees the winner's row**, not merely that the loser got a 409 —
      the two isolation levels are indistinguishable by outcome alone

      connection reads *outside* the caller's transaction and therefore outside the lock — **it looks
      like a re-read and is not one.** […]
~~~
