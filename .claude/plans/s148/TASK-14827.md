## Plain language — why

**The problem.** After TASK-14826 the Rule Engine computes only with the agreement rules each request carries. Payroll's requests carry none today, so on this branch every payroll calculation is refused. Payroll must now do what ADR-043 D12 decided: for each day of a month, find the rules in force that day (the agreement's published version, the position override, and the institution's local profile, central → position → local), and hand them to the engine.

**What this task does.** Payroll already cuts a month into stretches whenever something about the employee changes (an OK version, an agreement, a position, a transfer, a configuration version's "applies from" date, a local profile becoming active): those are the plan's segments, and since TASK-14818, 14822 and 14825 every one of those six is a cut. For each stretch it now asks TASK-14825's dated lookup for the rules in force, with the employee's **own dated record** (agreement, position, organisation), never the request body, and sends them with each piece of the timeline and with each per-segment call. If the configuration database cannot be read, or no published version is in force for a day, the month is refused by name before anything is calculated or written.

**Worked example.** An HK employee in June 2026 (OK26). Institution STY01 has a local profile with a 30-hour weekly norm; STY02 has one with 32 hours. HR transfers the employee to STY02 from Monday 15 June 2026.
- TASK-14822 cut June at the 15th (two segments). For **1–14 June** payroll asks the lookup for (HK, OK26, no position, STY01) as of 1 June and gets HK's published version with STY01's 30-hour norm; for **15–30 June**, (HK, OK26, no position, STY02) as of 15 June, with 32 hours.
- The timeline call carries two pieces, each with its own rules; the supplement and on-call calls for each segment carry that segment's rules. Each part's norm lines follow its institution (AC-C13a's pay half, TASK-14828-T).
- **Today** both parts would be priced on the compiled HK rules, 37 hours, whatever the institutions set.

**Replay, until TASK-14830 (ruling 11).** A replay re-runs a month already paid, to prove its figures. From TASK-14826 the engine refuses a piece without rules, so a replay must hand it rules too, and it must find them without reading today's employee records (owner ruling R42: a replay never consults today's profile history). So each calculation now also writes down, on each piece it freezes, **the organisation** the employee belonged to (`FrozenPiece.OrgId`). A replay asks the lookup for the rules in force today for exactly the frozen keys (agreement, OK version, position, organisation), and the existing fingerprint check refuses it by name if those rules have changed since. TASK-14830 later freezes the rules themselves and retires this re-resolution. *The honest limit,* recorded and told to the owner, not built around: the fingerprint is one hash over the set of rules a month used, so it cannot see two pieces of one month swapping rules; it would bite only a month calculated after the stack with two distinct rule sets, replayed before TASK-14830, with a retroactive publish in between, and no route replays today.

**One wire detail (ruling 15).** Payroll writes enumerated values (such as the config's `NormModel`) as words; the engine reads them only as numbers. The rules payroll now sends carry the first such value, so without care every calculation would be refused. Payroll therefore sends the engine's requests with enumerated values as numbers, and reads the answers as today.

**What does not change.** The arithmetic (the engine's), the plan and its segments (14818's and 14822's), the frozen inputs' shape apart from the one member above (the rest is TASK-14830's), the hours reads, the refusals already in place. On the seeded data every configuration the lookup returns equals the compiled one (PIN-2), so **every demo payslip is unchanged** (PIN-1) and so is every recorded fingerprint.
