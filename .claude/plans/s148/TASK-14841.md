## Plain language — why

**The problem today.** On the Skema page an employee can delete a number from a cell, and the cell looks empty. But the page never tells the server: it skips empty cells when it builds the save, and then, on the save's success, records the cell as empty anyway. When the month reloads, the value is back. For work periods it is the opposite and worse: removing every period of a day, or pausing while every period is half-typed, sends an empty day that the server stores.

**What this task changes, the screen half of "empty a cell".** TASK-14840 gave the save request a `cleared` member and made a removal real on the server. This task makes the screen use it:
- **A cell** (a project entry or an absence) emptied or set to 0 is sent as a removal, under `cleared`. The success path then tells the truth.
- **A day's work periods:** the day is sent as a removal only when **every period row is gone**. While the rows are merely half-typed, nothing is sent, and the stored day stands. (From 14840 the server refuses an empty work day, so this is also what keeps the screen's saves valid.)
- **One behaviour per answer:** if the server refuses the removal itself (422, for example a child's first sick day that the second day depends on), the value comes back with the server's message. If the month was sent meanwhile (409), or the save fails (5xx, network), the cell stays empty under the usual "not saved" alert and the removal is retried, like any failed edit.
- **Announced once:** after a successful removal of something that was really saved, a polite screen-reader line says *"Registreringen er fjernet"*.

**What does not change.** No confirmation dialog and no undo button (the owner was told, NR-A9): a removal is as reversible as any edit; retyping the value registers it again. A locked month is read-only, as today. The autosave timing (one second after the edit) is unchanged.
