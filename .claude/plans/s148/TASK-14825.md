## Plain language — why

**The problem.** A "configuration" is the set of rules an agreement applies (the weekly norm, the flex cap, whether overtime exists, the compensation model). It comes in three layers: the central agreement config, a position override (a variation for one job title), and the institution's local profile. One service, `ConfigResolutionService`, stacks the three for the screens. Today it has three faults:
- **It reads "the current version", not "the version in force on the day being shown".** Since wave 4 a GlobalAdmin can date a new version into the past, so a screen showing October can show November's rule.
- **It fails open.** When the database read fails, or finds nothing, it silently uses rules compiled into the code; when a position override is switched off, it silently brings back the compiled override (A-9); when the local profile cannot be read, it silently skips it. A value nobody chose is shown as if it were the rule.
- **Payroll cannot use it yet.** The payroll service registers it but cannot build it, because two repositories it needs are not registered (QUAL-184); and three old helper methods exist that only tests call (QUAL-042).

**What this task changes (T14a; the refinement's C-1, P-13).**
- **One lookup, asked "for this day".** It stacks central → position → local exactly as today, but each layer is the one **in force on that day**: the central version in force, the override version in force (TASK-14818's version history, NR-P8), and the local profile in force for the organisation the employee belonged to that day (TASK-14820's dated organisation, C-13).
- **Fail-closed.** A failed database read is refused as "unavailable". A day on which no published central version is in force is refused by name. No compiled value is ever substituted. An override or profile that is simply absent on that day is not an error: it means "no override" or "no local change", as today. **Every screen that reads a configuration, directly or through the per-day norm, answers the same two fixed errors through one Backend mapping** (B4), so a screen the lookup reaches only indirectly (the Skema month, say) still names the refusal instead of failing anonymously.
- **The four Backend reads move onto it**, each as of the day it already reads: the overtime compensation model and choice (as of 1 January of the period year, **with that day's own OK version**, B12), the per-day norm calculator (each day), the year overview's weekly-norm header (today) and the organisation's effective-configuration screen (today).
- **The three old helpers retire**, with the tests that only test them.
- **The payroll service registers what the lookup needs**, so it can be built (QUAL-184), ready for the engine switch (T14b) that makes payroll call it.

**What it costs, accepted on purpose (B6).** Resolving each day on its own means about three configuration reads per weekday: roughly 66 for a Skema month and 780 for a year overview, where today's per-month cache saved most of them. That is correct now and registered as a performance limit; TASK-14828 restores reuse per stretch of unchanged days.

**What does not change.** No payslip changes: payroll still prices on compiled rules until the T14b stack. The two month figures (Teamoversigt's expected norm and the balance summary's month norm) keep today's reads until TASK-14828 (B-9). On the seeded data no screen value changes: every seeded version applies from `0001-01-01`, so "in force on day X" and "the current version" are the same row.

**A worked example: one employee, two days.** An AC / OK26 department head (position `DEPARTMENT_HEAD`) works in organisation STY02. The seeded override for (AC, OK26, `DEPARTMENT_HEAD`) caps flex at 200 hours from `0001-01-01` (`docker/postgres/init.sql:1774`, its version row from `:1781`). A GlobalAdmin lowers that cap to 100 hours from Monday 26 October 2026, then raises it to 120 hours from Monday 2 November 2026 (TASK-14818 keeps every version). STY02's local profile for AC / OK26 sets no flex cap.
- **Asked for Friday 30 October 2026:** central = the AC / OK26 version in force that day (the seed, cap 150 h: `max_flex_balance` 150.0 in the AC / OK26 seed row, `docker/postgres/init.sql:1633`, equal to the compiled `MaxFlexBalance = 150.0m`, `CentralAgreementConfigs.cs:105`; checked at `bb529e62` under § 6 of the adjudication); position = the override version in force that day (100 h); local = STY02's profile in force that day (no cap) → **100 h**.
- **Asked for Monday 2 November 2026:** the same, with the override version of 2 November → **120 h**.
- **Today's code** answers 120 h for both days (it reads the override's current row), and if the database read fails it answers the compiled override's 200 h without saying so.
- **If the database cannot be read**, the lookup answers "unavailable" and the screen says so. **If AC / OK26 had no published version in force on the 30th** (say, a database-only agreement first published from 2 November), the 30th is refused by name.

**Who notices what.** An employee: nothing on the seeded data; once a dated version exists, each day of the Skema month and the year overview shows the norm of its own day. Everyone: if the configuration database cannot be read, or a day has no published configuration in force, every screen that reads a configuration (the overtime choice, the year overview, the organisation's configuration screen, and, through the per-day norm, the Skema month and save and the profile revaluation) shows its existing error state with a fixed English sentence instead of a value nobody chose (B4; Danish copy for these two errors is not built, and the owner is told). Payroll: no payslip changes; from this merge the payroll service's planner starts splitting a month at a dated version (TASK-14818's hydration, switched on by the registration), while it still prices both parts on compiled rules until T14b (BC-9).

## The rule

**A transaction whose first statement is a blocking advisory-lock acquire must pin
`IsolationLevel.ReadCommitted` explicitly — never the default overload.**

`pg_advisory_xact_lock` blocks until granted. Under REPEATABLE READ the transaction snapshot is taken
**before** the lock is granted, so the winner's commit — *the exact thing the loser was waiting for* —
stays invisible, and the loser proceeds on pre-lock state. The lock serializes execution while the
snapshot silently un-serializes the data, which is the worst of both.

Concretely in S127: a losing sender would fail to see the winner's committed period row, take the
*create* arm instead of the *transition* arm, and collide on the unique constraint — while every
observable outcome (a 409, the same row/audit/event counts) looked identical to the correct path. That
is why the acceptance criterion for it needs a protocol-level test asserting *the loser's post-lock read
returns the row*, not merely that a 409 came back.
~~~

### 2. A deliberate limit is a `shortcut(<tag>)` comment
