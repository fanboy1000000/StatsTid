## Plain language — why
- **The seeder.** At every backend start, `EmployeeProfileSeeder` gives each active user who has no *open* profile row a default profile: full time, no position, valid from year 1 (`0001-01-01`). It was written in S31 to backfill people who never had a profile.
- **The defect (QUAL-267, H).** A person whose profile HR closed while they stay employed also has no open row.
  - **A person created through the admin screen** has a first profile row dated the day they were created, so the year-1 insert succeeds. From the next restart, payroll pays the days after the close as full time on an invented record instead of refusing the month (QUAL-265's 422 `payroll-employment-record-gap`). The "cannot register" list (HRP-015) no longer shows the person, and the invented row overlaps the real, closed profile.
  - **A person seeded by SQL** already has a year-1 row, so the insert collides with the unique start-date index. The seeder then logs a "lost concurrent-startup race" that never happened, at every restart.
- **The rule already in force.** A closed profile with an active user is a gap HR repairs, never a guessed record (QUAL-265; HRP-015; `docs/operations/hr-follow-up-process-register.md:400-402`: the boot seeders cannot be the fix for gaps).
- **The fix.** The seeder backfills only users with **no profile row at all**. A person whose profile was closed is left alone, so the refusal and the list keep firing until HR enters a new profile.
- **Worked example.**
  - Anna is created through the admin screen on 2 March 2026, so her profile runs from 2 March. HR closes it on 16 March and she stays active. The backend restarts on 20 March.
  - **Before this task:** the seeder writes `[0001-01-01, open)` at 1.000. March then pays 16–31 March as full time.
  - **After this task:** the seeder writes nothing, and March answers 422 `payroll-employment-record-gap` until HR enters a profile.
  - **Bo, a brand-new user** created by SQL with no profile row at all, still gets the year-1 row at the next start.
