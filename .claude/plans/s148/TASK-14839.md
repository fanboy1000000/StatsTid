## Plain language — why

**What the demo gets.** S148 lets people record three new things: a local administrator sets the institution's own flex settings on its local profile (C-4) and lists its customary days off (C-10), and HR records two facts per person, the overtime regime and whether the person is on the flex scheme (C-11). The demo world, which the owner and testers use to try StatsTid, has none of them, so those screens are empty there. This task makes the demo generator write example rows:
- **a local profile** for every demo organisation, agreement and OK version, with the 37-hour plus cap set and nothing else;
- **three customary days** per organisation: 5 June as a paid day off, 24 December, and one closure day;
- **the two HR facts** for every demo person: HK and PROSA "overtime", AC by job category, everyone on the flex scheme.

**Why it must not change a single payslip.** The sprint's acceptance test (PIN-1) builds two demo worlds with this same generator, runs payroll on every month the demo approves, and compares the result with a golden file byte for byte. The new rows land in exactly those worlds. Three things keep pay identical:
1. **No random draw.** The generator uses one seeded random sequence in a fixed order. One extra draw before the last existing one would reshuffle who works which month with which outcome. The new rows are computed only from facts already drawn (each person's agreement and category, each organisation, the reference date).
2. **Nothing pay reads changes.** The profile sets only the plus cap, which no calculation reads in S148. Its four older columns, which do reach pay (the weekly norm, the flex cap, the overtime ceiling, pre-approval), stay empty, so the lookup keeps the central values. Customs and HR facts have no reader before S149.
3. **No month gains a boundary.** A profile that starts inside a month splits that month in payroll. These start before any month the demo calculates.

**What it must also get right.**
1. **Only values the person's agreement allows** (ruling 18). The AC values come from ADR-024's rows, which spell the category "Fuldmægtig"; the demo spells it "Fuldmaegtig", so a straight match would miss every AC fuldmægtig (`REF:59`).
2. **One row per day and scope per organisation** (rulings 7 and 8): the three customs fall on different days.
3. **No double writes.** Start-up seeders already give every active demo user an organisation row, an agreement-code row and an employee profile. This task writes none of those.
4. **No reset deletes users** (the § 1b carry), so no extra delete is needed (contract item 8).

**What the review settled** (the W7 adjudication). The committed demo file that the demo stack loads is regenerated in this task, so the demo actually shows the new rows (W7 ruling 1). The three new blocks have one fixed shape, so the tests can find them and strip them out again (W7 ruling 11). Each customary day's key is computed from its organisation and its day, so loading the file twice adds nothing (W7 ruling 8). The profile rows spell out the four pay-relevant columns as `NULL`, so "no pay effect" can be read in the file itself (W7 ruling 4).

**Worked example** (the June 2026 world PIN-1 measures: reference date Wednesday 15 July 2026, seed 45; its activity month opens Monday 1 June 2026, under OK26, which applies from Wednesday 1 April 2026).
- *Profile.* STYX1 gets six rows (AC, HK, PROSA × OK24, OK26), each with the plus cap 37 h and every other column empty, from Monday 1 January 0001, the history anchor (W7 ruling 4). Payroll prices June under OK26 and finds the (STYX1, AC, OK26) row in force all month. The row sets nothing pay reads, so June uses the central values; and no row starts inside June, so June is not split.
- *Customs.* For each organisation (W7 ruling 5): 5 June every year (Friday 5 June 2026) and 24 December every year (Thursday 24 December 2026), each a paid day off for the whole day, given to everyone; and one closure day, Friday 15 May 2026 (the Friday after Ascension Day, Thursday 14 May 2026). All three are valid from Thursday 1 January 2026.
- *HR facts.* An AC "Specialkonsulent" gets DISCRETIONARY and an AC "Standard" gets no value, shown as missing. An HK "Fuldmaegtig" gets OVERTIME (for HK the category does not matter). `demo_admin` (AC, Kontorchef) gets NONE. Everyone is on the flex scheme, from 1 January 0001.
- *Pay.* PIN-1's June 2026 text equals `demo-2026-07-15.golden.txt` byte for byte, as before.

Routing the failure into the exit code catches a loader that *knows* it failed. It does nothing for a
loader that is wrong about what success means — wrong month, wrong status, row silently absent.

**Both halves are required:**

1. **Failures reach the exit code.** A distinct non-zero code, with the failing items listed.
2. **The outcome is asserted against an independent oracle** — here, the database, keyed on the natural
   key `(employee_id, period_start, period_end)`, with per-status counts derived from the manifest. Not
   the tool's own report of what it did.

and the failing row named. Under the old counters that run was byte-identical to a healthy one.
## Checklist for any load/migration/seed tool

- [ ] Every failure path increments a counter that reaches a **distinct non-zero exit code**
- [ ] Verification asserts against an **independent** source of truth, on a natural key — not the tool's
      own log
- [ ] Counts are **derived from the input manifest**, so "produced nothing" cannot pass
- [ ] Assert the **negative** too: no row where the manifest says there should be none
- [ ] Run the verification on a **fresh load AND a rerun** — idempotent-skip paths are where masking lives
- [ ] Break the world deliberately; confirm **every** arm fires; document any arm that does not
