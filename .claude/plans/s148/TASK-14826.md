## Plain language — why

**The problem.** The Rule Engine is the part of StatsTid that turns registered hours into pay lines (norm, overtime, flex, supplements) and into rest findings (the 11-hour check). Today it looks up the agreement's rules in tables compiled into its own code (`RuleRegistry.cs:254`, `:393`, `:446-449`; engine `Program.cs:141-142`, `:151-152`). So nothing an administrator sets in the agreement editor, the position-override page or an institution's local profile reaches a payslip, and an agreement an administrator creates cannot be paid at all: the engine answers "No agreement configuration exists" (`RuleRegistry.cs:446-447`). ADR-043 D12 decided that the editors' values are the pay inputs.

**The decision (P-13, R-8).** The engine stops looking anything up. Every route that needs an agreement's rules (five of them) takes them **in the request**, and a request that brings none is refused with a fixed sentence, so a caller that forgets is stopped loudly instead of quietly getting the compiled values. The engine also checks that the rules it is handed are **the piece's own** (the same agreement and OK version), so a caller that hands the wrong rules is refused, not obeyed. The compiled lookup class, `AgreementConfigProvider`, is deleted. Payroll (TASK-14827) and the Backend and the Orchestrator (TASK-14828) start sending the rules next; until they do, the stack's own branch has callers the engine refuses, which is exactly why the six tasks merge as one.

**The rest check, per day.** With dated configurations a month can hold two minimum-rest values (11 h until Sunday, 12 h from Monday). The research adjudication (RR-7) settled whose value judges what: **each work end is judged by the value in force on its own date**; the maximum-daily-hours check by its own day; the weekly-rest check's severity by its window's last day (ruling 4). The 48-hour check reads no configured value at all, so it has nothing to judge by any day and is unchanged (ruling 3).

**Worked example.** An HK employee in March 2026 (OK24). An administrator publishes a new HK version with a minimum rest of 12 h, applying from Monday 16 March 2026. The Backend (TASK-14828) sends the compliance check two runs: 1–15 March under the 11 h version, 16–31 March under the 12 h version.
- Saturday 14 March 10:00–20:30, Sunday 15 March 08:00–14:00: the Sunday work ends at 14:00 after 11.5 h of unbroken rest (20:30–08:00). Sunday's value is 11 h: **no finding.**
- Sunday 15 March 10:00–20:30, Monday 16 March 08:00–14:00: the Monday work ends after the same 11.5 h. Monday's value is 12 h: **a finding dated Monday 16 March.**
- Today the engine reads the compiled 11 h for both and finds nothing on Monday.

**What does not change.** The arithmetic. A request carrying exactly the compiled rules gets exactly today's answer, so the evaluation marker stays `weekly-timeline-v3` (ADR-016 D10's marker convention: it moves when arithmetic moves) and every demo payslip stays the same (PIN-1). `evaluate-absence` reads no agreement configuration and is unchanged (BC-24). The fingerprint the timeline route returns is computed exactly as today, over the configs the engine actually used, so replay's check keeps working until TASK-14830 freezes the configs by value (`REF:820`; NR-P10).

**One defect fixed on the way (ruling 1; QUAL-190).** When a position has its own override (for example a department head's larger flex cap), a small SharedKernel function, `PositionOverrideConfigs.ApplyOverride`, builds the merged rules. It copies 34 of the rules' 41 members and silently drops seven, among them the minimum rest and whether rest may be shortened, which then fall back to built-in defaults. Today nothing notices: the engine only ever merges the four compiled AC overrides, and AC uses every default. From this stack on, every override an administrator saves in the database reaches pay and the rest check through this function, so an HK employee in such a position would have rest warnings turned into violations and a configured minimum rest reset to 11 h. The fix is seven lines in this task, the stack's first commit (item 12), and TASK-14826-T adds a test (AC-C1p) that fails whenever a member is left out, including a member added later. No seeded value moves, so no payslip and no fingerprint changes.

## Decision
The rule engine consists exclusively of pure functions with no I/O, no database access, no HTTP calls, and no ambient state. All inputs are passed as parameters; all outputs are return values.

## Rationale
- Pure functions guarantee deterministic replay — same inputs always produce same outputs
- No I/O means rules can be tested in isolation without mocks or infrastructure
- Separation from infrastructure ensures rule logic is never coupled to persistence or network concerns
- This is Priority #2 in the system (after architectural integrity)

## Consequences
- Rule engine code (`src/RuleEngine/**`) must never import I/O libraries or infrastructure namespaces
- Calendar data, agreement configs, and OK versions must be passed as parameters, not fetched
- Any new rule must be provably deterministic via unit tests
- Rule engine cannot be modified by the Security agent or any infrastructure change

Because normalization moves a crossing's post-midnight half to `Date = D+1`, a crossing on the LAST day of a

must be a documented exclusion.
