## Plain language — why

TASK-14839 makes the demo generator write example rows for three new S148 features: a local profile per organisation, agreement and OK version carrying only the 37-hour plus cap; three customary days per organisation; and the two HR facts for every demo person. The owner's acceptance test, PIN-1, runs payroll on worlds built by this same generator and must not move by one byte. You prove two things.
- **AC-C12a, the DemoSeed suite.** The generator is still deterministic. Its SQL output changed **only by the added rows**: every existing line is identical and the manifest is unchanged, which shows no random draw moved. And the new rows are the right ones: one profile per key with only the plus cap and every pay-relevant column empty, three customs per organisation with no two on the same day, and one HR-facts row per person with the value that person's agreement and category give.
- **AC-C12b, PIN-1 final.** Both demo worlds still produce their golden pay text, byte for byte, at the recorded seeds, now with the new rows in them. CI runs it at C-2. Nobody re-pins the golden. Ruled (W7 ruling 15): before comparing, PIN-1 first checks that the world really carries the new rows, so a pass cannot come from a world that lost them.
- **AC-C12c, the allowed values** (W7 ruling 16). Every demo person's overtime regime is one the product's own rules allow for that person's agreement. The check goes through those rules, not through a copy, so the demo goes red if the rules ever change under it.
- **The committed demo file** (W7 ruling 22). The demo file in the repository, which the demo stack loads, must equal what the generator produces at its pinned defaults. No test checked it before, which is how it could go stale unnoticed.
