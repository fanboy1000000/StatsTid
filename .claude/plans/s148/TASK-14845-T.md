## Plain language — why

**What TASK-14845 changes.** Before a write handler changes something about a person, it asks "may this administrator act on this person?" from a read taken before it locks anything. If a colleague transfers the person to another institution in that moment, the write still lands, on someone the administrator was never checked for. TASK-14845 makes 22 write actions compare, under a lock, the organisation the check approved with the organisation the lock found, and refuse with 409 "refresh and retry" when they differ. TASK-14820-T and 14821-T proved the same refusal on the user edit and six more writers.

**What you prove, 22 times.** For each action you force exactly that interleaving, deterministically, and show the request answers 409 with exactly one sentence and writes nothing. A test that passes only when the timing happens to be lucky proves nothing, so the test, not the scheduler, decides the order: it holds a lock the request needs, waits until PostgreSQL shows the request waiting on that lock, moves the person to Styrelse STY02, commits, and only then lets the request go on.

**Two ways to make the request wait (R6).**
- **Where the request locks the person's row** (tiers 2 and 3, fourteen sites): the test holds that row, exactly as `TransferRaceTests` does for the user edit.
- **Where the request locks the reporting tree instead** (tier 1, eight sites): there is no row wait to borrow. The suggested blocking point is earlier: the test holds the `organizations` table, so the scope check stops between reading the person and reading their organisation. The person is moved while it is stopped. If a site has no point where the request reliably stops, you **stop and report**; you never fall back on a sleep.

**Why the mutations matter.** Each fact is shown red once in CI with the compare removed and everything else kept (M-46 for the nine sites in files S148 already changes, M-47 for the thirteen the owner added). A fact that stays green under its mutation does not test the guard.

Expected values come from the plan and the briefs, never from what the code returns.
