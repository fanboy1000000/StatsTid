## Plain language — why

TASK-14832 lets a LocalAdmin save eighteen new settings on the institution's local profile (flex caps and periods, office hours, the credit basis for paid absence), checks every value on the way in, and widens the "did anything change?" test from four settings to twenty-two. You prove five things, each with a test that fails on the code before the change:
- **AC-C4a:** each new setting is stored, comes back on a read, and appears in the audit row's list of changes.
- **AC-C4b:** a negative cap, a weekday window that ends before it starts, and "credit by office hours" with no office hours are each refused (400), and nothing is stored.
- **AC-C4e:** a same-day save that changes only one new setting makes a new version, one audit row naming that setting, and one event; so does a save that clears a setting that was set (ruling 15); and a save that changes nothing is still a no-op. Today such a save is silently dropped.
- **AC-C4f (SEC-061):** the old fields' bad values (a weekly norm of 0 or −5, a negative flex or overtime maximum) are refused with nothing stored, while 0 for the two maxima and "not set" everywhere are accepted.
- **AC-C4g (ruling 15):** a value the table would reject or could not hold exactly (a third decimal, a number too large for its column, a misspelled option, a weekday with only a start time, a clock time with seconds) is refused (400) with nothing stored, while the column's own largest value and a number written with a trailing zero are accepted.

**Worked example (AC-C4e, one of its eighteen cases).** STY01's profile for test key `C4E03`/OK24 runs from Monday 2 March 2026 at version 1, with office hours set and no plus cap. On Thursday 5 March 2026 the test saves the same profile with the plus cap 37 and nothing else changed. Expected: 200 at **version 2**; one `MODIFIED` audit row whose delta is exactly `{"FlexPlusCapHours": {"Old": null, "New": 37}}`; one `LocalAgreementProfileChanged` outbox event naming the same one setting; the stored plus cap 37. On the code before TASK-14832 the same request answers 200 at **version 1** and writes nothing: the version assertion fails, which is the RED.

Two existing tests also change: the response contract pin now expects thirty-one members, not thirteen, and one old migration test needs the new columns in its hand-built table. Neither weakens what it checks. **You never touch AC-C2u's two facts**, the ones the stale-predecessor mutation M-49 must keep turning red.
